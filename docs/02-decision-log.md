## D-1. エディタのハイライトはトークン列にする（AST にしない）

**決めたこと**
`MarkdownCore` は「ソース上の範囲 + 種別」の平たい列だけを返す。ネストしたドキュメント木は持たない。

**理由**
エディタが必要とするのは `NSTextStorage` に属性を貼るための範囲だけ。
打鍵ごとに再計算するので、軽さが正義。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| AST を持つ | 実装量と再計算コストが上がる。エディタに木構造は要らない |
| `AttributedString(markdown:)` を使う | 範囲情報が取れず、記法文字を薄く表示するといった制御ができない |

**代償**
プレビューの描画には使えない。→ [D-4](#d-4-プレビューは-swift-markdown-で描く) で別パーサを立てることになった。

**副産物**
1行の解析が「直前の行の状態」だけで決まる形にしたので、差分更新を後から載せられる。
`MarkdownBlockState` は 6 通りしかない。

## D-2. トークンは重なることを許す

**決めたこと**
`# **見出し**` は見出しトークンと強調トークンの両方を生む。
配列は**外側が内側より先**に並ぶ。

**理由**
重なりを禁じると、生成側が範囲を分割する処理を持つことになり複雑になる。
一方、属性の適用は配列順に貼れば内側が外側を上書きして自然に正しくなる。

**気をつけること**
配列を位置順にソートし直すとこの保証が壊れる。
太字・斜体は「上書き」ではなく「足す」必要がある（`PlatformFont.addingTraits`）。

## D-3. 対応記法は CommonMark 基本 → 後から GFM 拡張を追加

**経緯**
当初は CommonMark 基本セットのみで実装。後から GFM 拡張が必要と判明して追加した。

**追加時に設計を変えずに済んだ点 / 済まなかった点**

| | 影響 |
|---|---|
| 取り消し線・タスクリスト | トークン種別を足すだけ。設計変更なし |
| 拡張オートリンク | インライン走査に分岐を足すだけ |
| **表** | **公開 API の変更が必要になった** |

表のヘッダ行は「次の行が列数の一致する区切り行である」ことでしか判別できない。
そのため `tokenizeLine` に `nextLine:` を足して1行だけ先読みする形にした。

```swift
tokenizeLine(text, range:, stateBefore:, nextLine:)
```

後ろ向きの参照は入れていないので、差分更新の打ち切り判定（`stateAfter` の収束）は成立したまま。

**教訓**
「対応記法の範囲」は着手前に確定させておくべきだった。データモデルには影響しなかったが、
API の形は変わった。

## D-4. プレビューは swift-markdown で描く

**決めたこと**
`apple/swift-markdown`（cmark-gfm のラッパ）を `NullnoteUI` の依存に追加し、
AST から SwiftUI ビューを組む。

**理由**
GFM の表を含む準拠した解析がタダで手に入る。プレビューは打鍵ごとには走らないので速度要件が緩い。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| `AttributedString(markdown:)` | **表を表現できない**。GFM 対応を決めた時点で不可 |
| cmark-gfm → HTML → `WKWebView` | CSS でテーマを作れるが、テーマの二重管理と WebView の起動コストが付く |
| 自前レンダラ | 依存ゼロだが実装量が大きい。得るものが釣り合わない |

**守った境界**
依存は `NullnoteUI` 止まり。`MarkdownCore` は Foundation のみのまま。
エディタのハイライト経路に外部依存は入っていない。

## D-5. 裸の URL は `NSDataDetector` で補う

**問題**
swift-markdown が有効にしている cmark 拡張は `table` / `strikethrough` / `tasklist` の3つだけで、
**`autolink` は有効になっていない**。一方 `MarkdownCore` は裸の URL をリンクとして着色する。
このままエディタとプレビューで見え方がずれる。

```
Sources/Markdown/Parser/CommonMarkConverter.swift:624-626
    cmark_parser_attach_syntax_extension(parser, cmark_find_syntax_extension("table"));
    cmark_parser_attach_syntax_extension(parser, cmark_find_syntax_extension("strikethrough"));
    cmark_parser_attach_syntax_extension(parser, cmark_find_syntax_extension("tasklist"));
```

**決めたこと**
`PreviewModel` 側で `NSDataDetector` を使って後から補う。

**注意点**
`NSDataDetector` は GFM より貪欲で、`example.com` 単体も拾ってしまう。
`MarkdownCore` と同じ条件（`http://` `https://` `www.` またはアットマークを含む）まで絞り込んでいる。
両者の判定条件がずれると、また見え方が食い違う。

## D-6. プレビューはデバウンスする（同期パースにしない）

**測ったこと**（release ビルド / Apple Silicon）

| 文字数 | `MarkdownTokenizer.tokenize` | `PreviewBuilder.build` |
|---|---|---|
| 500 | 0.06 ms | 0.47 ms |
| 1万 | 1.0 ms | 9.2 ms |
| 5万 | **5.3 ms** | **45.7 ms** |

**判断**

- **プレビュー**: 5万文字で 45.7 ms。1フレーム（16.7 ms）の約3倍なので、
  `body` 内での同期パースは不可。入力が止まって 150 ms 後に解析する
  （`task(id:)` は値が変わると前のタスクを取り消すので、先頭で待つだけでデバウンスになる）。
- **エディタ**: 5万文字で 5.3 ms。1フレームに収まるので、打鍵ごとに全文を貼り直して問題ない。
  **差分更新は実装しない。** 必要になってから入れる（設計上は載る形にしてある）。

**教訓**
「重そうだから最適化する」ではなく、測ってから決める。
エディタ側は測った結果、最適化が**不要**と分かった。

> **追記（D-24）: この判断は間違っていた。**
> 上の 5.3 ms は**トークン化だけ**の値で、属性を貼る費用も、
> それによって捨てられるレイアウトの費用も入っていない。
> 実際には打鍵1回で 30 ms かかっていた。差分更新を入れて 3.6 ms にした。
> **測る対象を間違えると、正しく測っても結論を誤る。**

## D-7. `.xcodeproj` は手書きし、ファイル同期グループを使う

**決めたこと**
`project.pbxproj` を手で書いた。`Nullnote/` は `PBXFileSystemSynchronizedRootGroup`。

**理由**
Xcode GUI を使わずにプロジェクトを作る必要があった。
Xcode 16 以降のファイル同期グループなら、**ディスクにファイルを置くだけでターゲットに入る**ため、
`.swift` を1つ足すたびに pbxproj を編集する必要がない。

**構成上の工夫**
`Info.plist` と `.entitlements` は同期グループの外（`Supporting/`）に置いた。
同期グループの中に入れると、リソースとしてコピーされる恐れがあるため。

**注意**
pbxproj の ID は 24桁の16進。手書きするなら重複しない規則を決めておくこと
（このプロジェクトは `AA00000000000000000000xx`）。

## D-8. 日本語ロケールを宣言する

**問題**
自作のメニュー項目は日本語なのに、標準メニューが「File」「Edit」のまま出て混ざっていた。

**原因**
アプリが対応ロケールを宣言していないと、AppKit は標準メニューを英語で出す。

**対処**
`Info.plist` に `CFBundleDevelopmentRegion = ja` と `CFBundleLocalizations = [ja, en]`、
pbxproj の `developmentRegion` を `ja` に。
→ 「ファイル」「編集」「表示」「ウインドウ」「ヘルプ」になった。

## D-9. サンドボックスは最初から有効にする

**決めたこと**
`com.apple.security.app-sandbox` と `files.user-selected.read-write` を最初から入れた。

**理由**
App Store 配布の必須要件。後から有効にすると、それまで通っていたファイルアクセスが
軒並み止まって直すのが大変になる。

**現状**
署名はローカル実行用のアドホック。配布時に Developer ID / App Store の証明書へ差し替える。
そのとき `com.apple.security.get-task-allow`（デバッガ接続用）が残っていないか確認すること。

## 実装中に見つけた不具合

記録として残す。同種の間違いを繰り返さないため。

### B-1. `~~~b~~~` が取り消し線として誤解析される

チルダ3連続を「フェンス記号だから取り消し線ではない」と弾いた後、
**1文字だけ進めて同じ連続の内側から数え直していた**ため、
`~~` + `b~` + `~~` と解釈されていた。

**修正**: 弾くときは連続全体を読み飛ばす（`InlineScanner.appendStrikethrough`）。

**教訓**: 「条件に合わないので nil を返す」と「消費せずに次へ」は違う。
走査位置を進める量まで含めて考える。

### B-2. プレビューの取り消し線とインラインコードが見た目に出ない

`inlinePresentationIntent` に `.strikethrough` / `.code` を載せていたが描画されなかった。
**SwiftUI の `Text` が実際に描くのは強調と強い強調だけ。**

**修正**: 意味づけとは別に、具体的な属性（`strikethroughStyle`、`font`）も指定する。

**副作用**: インラインコードのフォントに解析時点の文字サイズが焼き込まれるため、
文字サイズが変わったときもプレビューを組み直す必要が生じた
（`MarkdownPreview` の `task(id:)` のキーに `fontSize` を含めた）。

**教訓**: 「意味づけを載せれば描いてくれるはず」を信じない。目で見て確かめる。

### B-3. `ImageRenderer` では `task` が走らない

オフスクリーン描画で確認しようとしたら、プレビューが真っ白になった。
`ImageRenderer` はビューのライフサイクルを回さないため、`task` 内の解析が実行されない。

**対処**: `NSHostingView` をウインドウに載せ、ランループを回してから `cacheDisplay(in:to:)` する。

**教訓**: 非同期に中身を組むビューは、同期的にスナップショットできない。
印刷や画像書き出しを実装するときも同じ問題が出る。

## D-30. ファイル名を変えたら、先頭の見出しも合わせる（設定で切り替え）

**きっかけ**
ファイル名と、文書の1行目の見出しは、たいてい同じものを指している。
片方だけ直すと食い違う。運用上の改良点 [#012]。

**決めたこと**

| 場面 | どうするか |
|---|---|
| 1行目が `# 見出し` | 見出しの本文だけ差し替える（`#` と閉じの `#` は残す） |
| 1行目が見出しでない | 先頭に `# 名前` と空行を挿し込む |
| 名前が変わっていない（移動だけ） | **何もしない** |
| 設定が切ってある | 何もしない。**既定は切ってある** |

本文を黙って書き換える動きなので、**既定はオフ**。選んだ人にだけ効かせる。

### 「先頭の見出し」は1行目だけを見る

文書のどこかにある最初の見出しまで拾う案は捨てた。
本文を書き進めたあとの改名で、**遠く離れた行が黙って書き換わる**。
空行を除いた最初の行に限れば、何が起きるか読める。

### `#` は自分で数えない

行の解釈は `MarkdownTokenizer` に任せた。自前で数えると、
コードブロックの中の `# コメント` や、引用の中の `> # 見出し` を見出しと取り違える。
`##` 以下は「先頭の `#` のタイトル」ではないので、差し替えではなく挿し込みに回す。

### 改名にどうやって気づくか

SwiftUI の `DocumentGroup` は改名を知らせてこないが、**`fileURL` は変わる**。
Finder での改名（`mv`）でも更新されることを実測で確かめた。
すでに外の変更の見張りを `.task(id: fileURL)` で張り直していたので、
**同じところで気づける**。`NSDocument` 側に手を伸ばす必要は無かった。

前の名前を覚えておき、値が変わったときだけ動かす。
**新規書類をはじめて保存したとき（`nil` → ファイル）は動かさない。**
名前を「変えた」のではなく「付けた」場面なので、本文は触らない。

### 順序を間違えると、直した見出しが合流で消える

`.task` の中では、**見張りを張り直すのが先、見出しを直すのがあと**。

`startWatching()` は「いまの本文＝ディスクの内容」として `lastSyncedText` を置く。
先に見出しを直すと、**直したあとの本文が「ディスクと一致していた内容」として記録される**。
その状態で外のソフトがファイルを書くと、合流の基準が狂い、こちらの直しが差として現れず消える。

実測での確認: 改名で `# 買い物リスト` を挿し込んだ直後に、
外から本文へ1行足したところ、**見出しも追記も両方残った**（印は入らない）。

### 直した結果は保存しない

自動保存は捨てた。未保存の編集として残せば、気に入らなければ ⌘Z で戻せて、
よければ ⌘S で確定できる。**黙ってディスクを書き換えないほうが、取り返しがつく。**

### 縛ったこと

`TitleSync` は副作用を持たない関数にして、テストで縛った（16件）。
とくに「**1行目より下は、どの場面でも動かない**」ことを見ている。

## D-29. プレビューは見えているところだけ組む。脇の領域は畳んでも外さない

**決めたこと**
プレビューのブロックを `LazyVStack` で並べ、画面に入ったものだけ組む。
測った大きさは覚えておく。目次は閉じるときも**居場所を変えず幅を 0 にする**。

### プレビューはマスの数だけ `NSTextView` を作っていた

ブロックはどれも `NSTextView` を持ち（D-14）、表は**マスごと**に持つ。
20個の表（1300マス）を含む1.7万字の文書で 1341 枚。

さらに `Grid` は列幅を決めるのに各マスへ何度も大きさを尋ねる。
`sizeThatFits` はそのたびに TextKit で組み直していた。

| 手 | 枚数 | 組み立て＋描画 |
|---|---|---|
| いま | 1341 | 1290 ms |
| 測った大きさを覚える | 1341 | 945 ms |
| **＋見えているところだけ組む** | **135** | **218 ms** |

（release ビルド実測。段落だけの文書でも 301 枚 → 29 枚）

**費用は「開くとき」から「スクロールするとき」へ移る。** 消えたわけではない。
大きな表が画面に入る瞬間に 130 枚ほどまとめて作ることになる。
どちらも待てる長さに収まったので、ここで止めた。

**採らなかった手**

- **マスを SwiftUI の `Text` にする**（510 ms）… 表の中のリンクのホバーが消え、
  インラインコードの角丸の札（D-23）がただの文字になる。速さのために機能を削る形になる
- **表まるごとを1枚の `NSTextView` で組む**（`NSTextTable`）… 何も失わないが、
  罫線・列幅・横スクロールを作り直すことになる。いまの数字なら見合わない

### 脇の領域を `if` で出し入れしない

目次の開閉でエディタが作り直されていた。プレビューで踏んだのと同じ間違い。

```swift
if showsOutline { HSplitView { outline; mainArea } } else { mainArea }
```

これだと SwiftUI が `mainArea` を**別のビュー**とみなす。`NSTextView` が作り直され、
本文の貼り直しと組版が最初からやり直しになって、編集画面が一瞬消える。

`SidePane` を作り、閉じるときも並びを変えずに幅を 0 にした（`SplitPane` と同じ形）。
**中身は `if` で作らなくてよい。** 位置さえ動かなければ、見出しを拾い直す費用は省ける。

幅は**点で持つ**。比率だと窓を広げたときに目次まで広がる。

### 開け閉めの動きは短く。押したことは輪で返す

領域の幅が動いているあいだ、エディタは**毎フレーム本文を折り返し直す**。
文書が大きいほど重く、0.15 秒だとその回数ぶん引っかかる。0.1 秒に縮めた。

それでも 47 KB の文書では「押したのに何も起きていないように見える」状態だった。
ツールバーのボタンに、開け閉めのあいだだけ輪（`ProgressView`）を出すようにした。
アイコンと**重ねて不透明度だけ入れ替える**（ツールバーの項目は中身を入れ替えると
取り違えが起きる。D-21 で 🔍 を押すとプレビューが消えた）。

**輪は止まって見えることがある。** 遅さの正体が主スレッドの詰まりなら、
詰まっているあいだは輪も回らない。それでも「押した」ことは伝わる。

### 目次の描き方の作り直しは、効果を示せず見送った

階層のままビューを入れ子にすると `AnyView` が要り、`List` が行を遅らせて作れない。
平たい配列にすれば速くなるはず、と考えて書き直したが、
**計測で差が出なかった**（見出し 157 個で 748 ms → 748 ms）。
開閉の三角の見た目が変わるだけになるので、戻した。

遅さは目次の中身ではなく、幅が変わることによるエディタ側の折り返し直しだった可能性が高い。
次に触るなら、そちらを疑うこと。

### 仕切り線のドラッグが飛んでいた

`DragGesture` のずれは**掴んだ場所からの通算**なのに、そのときの幅に足し込んでいた。
動かすたびに二重に効いて、端まで飛ぶ。掴んだ時点の幅を覚えて、そこに足す。

## D-28. ⌘D の複数選択は自前で持つ。変換中は本文を触らない

**決めたこと**
`⌘D` で同じ語を1つずつ増やし、`⌃⌘G` で全部選ぶ。
選んだ全箇所に打ち込み・削除が効く。矢印キーでカーソルをそろえて動かせる。

| キー | 動き |
|---|---|
| `⌘D` | カーソルの語を選ぶ。押すたびに次の同じ語を足す |
| `⌃⌘G` | 文書中の同じ語を全部選ぶ |
| `←` `→` | 全部のカーソルをそろえて動かす。**複数選択は続く** |
| `⇧←` `⇧→` | 全部の選択を1文字ぶん縮める・伸ばす（**始点は動かさない**） |
| `⌫` `fn⌫` | 選んであればその範囲、カーソルだけなら隣の1文字 |

### `NSTextView` は複数選択を**見せてくれるだけ**

複数の範囲を選ぶことも、ハイライトを出すこともできる。
**ただし打っても削っても最初の1つにしか効かない**（実測）。書き換えは自前で全範囲に当てる。

さらに、**長さ0の選択はいくつ渡しても1つにまとめられる**。
消したあとの行き先はどれも長さ0なので、選択に預けたままだと消えてしまい、
続けて打った文字が先頭にしか入らない。だから打ち込み先を自分で持つ
（`FocusReportingTextView.targets`）。カーソルが動いたら捨てる。
余分なカーソルは見えないので、細い縦棒を自分で描いている（点滅はしない）。

### 語の切り出しは**文字種の変わり目**で

「文字が続くかたまり」を語にすると、日本語では句点まで丸ごと1語になる
（「ナイフを刺し入れ血を抜く」で1語）。同じ並びが他に無いので `⌘D` が効かない。

片仮名・平仮名・漢字・英数字が切り替わったところを境目にした。
形態素解析ではないので完全ではない（「お刺身」は「お」と「刺身」に割れる）。
思ったところで切れないときは、**選んでから `⌘D`** すれば任意の範囲を対象にできる。

検索欄と違い、**大文字小文字を区別する**。`Foo` を選んだつもりで `foo` まで書き換わると事故になる。

### 変換中に本文（記憶域）を触ると入力が壊れる

打っているそばから全箇所を動かしたくて、変換中に残りの行き先へ写してみた。**壊れた。**

AppKit は入力プログラムと本文の状態を突き合わせて動いている。
横から書き換えると整合が取れず、変換を捨てる。1文字ごとにやり直しになり、
「な」を打とうとするとローマ字の `n` が確定して `nな` になる。

段階を追って削ったが、どれも効かなかった。

| 試したこと | 結果 |
|---|---|
| `didChangeText()` を呼ばない | 直らない |
| `shouldChangeText` を通さない（取り消しに積まない） | 直らない |
| 未確定のぶんを置く範囲を明示して渡す | 直らない |
| 写しを当ててから `super` を呼ぶ／逆順にする | 直らない |

**記憶域を触った時点で崩れる。変換が終わるまで本文には手を出さない。**

代わりに、変換中の文字列を**上から描く**（`drawComposing`）。
書かずに描くので入力は壊れない。ただし後ろの文字を押しのけられないので、
**下に敷いてある文字は隠す**（元からあった語も隠す。半分だけ残ると別の語に読める）。
書体は打ち込む先から借りる。確定すればその属性を継ぐので、前後で見た目が飛ばない。

確定した時点で、決まった文字列が全箇所に広がり、そこで初めて行が組み直される。

### まだ先頭1か所にしか効かないもの

`⌥⌫`（単語ごと削除）、切り取り、貼り付け。**無言で片方だけ書き換わる**ので気付きにくい。
必要になった時点で塞ぐ。

## D-27. 画像の置き方は `{.…}` で指定する。回り込みは見送る

**決めたこと**
`![](…){.center}` のように、画像の直後の `{.…}` で置き方を指定する。
入れたのは**中央寄せとサムネイルの2つだけ**。回り込み（`{.left}` `{.right}`）は見送った。

| 指定 | 見た目 |
|---|---|
| 無し | 元の大きさまで。左に置く |
| `{.center}` | 幅いっぱい。**元より小さい絵は引き伸ばす** |
| `{.thumbnail}` | 120pt の正方形に切って並べる。押すと窓で開く |

**Markdown の標準ではない**
他のツールで開くと `{.center}` の文字がそのまま見える。
見た目の指定を本文に持ち込む以上、この割り切りは避けられない。
知らない名前（`{.wobble}` など）は黙って指定なし扱いにしてある。
あとで種類を増やしたときに、古い文書が壊れないため。

**回り込みを見送った理由**

中央寄せとサムネイルは「絵をどこに置くか」の話で、並べ方を変えるだけで済む。
**回り込みだけ質が違う。** 文章の行が画像の形に合わせて折り返す必要があり、
いまの「1ブロック＝1ビュー」（段落ごとに独立した `NSTextView`）では実現できない。

`NSTextContainer.exclusionPaths` を使えば TextKit の標準機能で組めるが、
**画像とその後ろの段落を1つのテキストビューにまとめる**構造変更が要る。
速度の問題ではなく（組版のたびに数 ms、しかも打鍵の経路には入らない）、土台の作り替えになる。

必要になった時点で、そのときの土台に合わせて入れる。

**空白ひとつで効かなくなった**

最初は `{.` の直後から `}` までを名前として読んでいた。
`{. center}` と書かれた文書で効かず、**なぜ効かないのか画面からは分からない**状態になった。
折り返し位置がちょうどその空白だったため、書いた側も気づきにくかった。

`{.center}` `{. center}` `{ .center }` `{.CENTER}` のどれでも読むようにした。
ただし `{center}`（ドット無し）は指定として扱わない。`{注釈}` と取り違えないため。

**拡大表示は窓にする。シートにしない**

サムネイルを押したときの拡大表示は、最初シートで出した。
**シートは利用者が大きさを変えられない。** 大きな絵を見るのに向かない。
独立した `NSWindow` に変えて、広げることも全画面にすることもできるようにした。
窓は1枚を使い回す（押すたびに増えると、閉じて回るのが手間）。

前後送りは**段落をまたぐ**。文書に出てくる画像を書かれた順に集めて配っている
（段落ごとのビューに持たせると、引用やリストの入れ子を通すたびに引数が増える）。
**端では止める。回らない。** 一覧を眺める操作で、いつのまにか先頭へ戻る方が分かりにくい。

## D-26. 画像は表示する。サンドボックスは外さない

**決めたこと**
`![](…)` の画像をプレビューに描く。書き方は**全部認める**
（文書からの相対・`~/`・絶対・`file://`・`https://`）。
読む許可は**フォルダ単位で一度だけ**もらい、ブックマークで覚える。

**まず確かめたこと**

このアプリはサンドボックスの中にいて `files.user-selected.read-write` しか持たない。
**文書を開いても、その隣にあるファイルは読めない。** 実機で確かめた
（画像のところに「読む許可がありません」と出た）。
絶対パスで表示できなかったのは、パスの解釈以前にここで止まっていたため。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| サンドボックスを外す | 許可のやり取りが要らず実装も単純。**App Store 公開を諦めることになる**（D-9） |
| 画像ごとに許可を聞く | 1枚ごとにパネルが出る。文書に10枚あれば10回 |
| 相対パスだけ認める | 移動に強く GitHub とも互換。ただし既に書いてある絶対パスの文書が全部書き直しになる |

**フォルダ単位のブックマーク**
利用者にフォルダを選んでもらい、セキュリティスコープ付きブックマークを保存する。
次の起動時に開き直すので、聞かれるのは一度きり。サンドボックスは有効なまま。

**許可される範囲は、利用者がパネルで選んだフォルダの配下すべて**

パネルは画像のあるフォルダを**開いた状態**で出す。そのまま「許可」を押すと、
選ばれるのは開いているフォルダ自身ではなく**その親**になりやすい。

実際、`猪はおいしい/` の画像を許可したつもりで、保存されたのは親の
`textstories/` だった。結果として、その配下の別の物語の画像も読めるようになる。

**これは意図した挙動として残す。** 文書ごとに聞かれるより実用的で、
利用者が上の階層を選び直して広く許可することもできる。
狭くしたいなら、パネルを出すときに対象フォルダ自身を選択状態にすればよい。

**「見つかりません」と「読む許可がありません」を分ける**
利用者がやることが違う。前者は書き間違い、後者は許可の問題。
**「許可する…」のボタンは後者にだけ出す。** 前者に出しても、押して直るものではない。

**「許可する…」のボタンは、アプリ全体の色を使わない**
本文の中に置かれる小さなボタンで、明るい黄色（`control`）だとライトの地に溶けて読めない。
記法の灰色（`quote`）に寄せて、本文より一段引いた見た目にした。

**網上の画像は読みに行く**
`com.apple.security.network.client` を足した。
**文書を開いただけで外部に接続する**ことになる（追跡用の画像なら、開いたことが相手に伝わる）。
利用者に判断してもらったうえで入れている。

**踏んだ落とし穴: 「画像1枚だけの段落」では狭すぎた**

最初は「画像1枚だけで出来た段落」を絵にしていた。ところが

```markdown
![一枚目](a.jpg)
![二枚目](b.jpg)
```

は、空行が無いので **Markdown では1つの段落**。条件から外れて代替テキストに落ちた。
「画像**だけ**で出来た段落」に広げ、複数枚は縦に積む形にした。

文字が混ざっている段落は絵にしない。文中の画像を絵にすると行の流れが切れる。

## D-25. 外の変更を取り込む。合流できないところだけ人に聞く

**きっかけ**
Claude Code など別のソフトで同じファイルを直すと、保存時に
「別のアプリケーションによって変更されました」が出て手が止まる。

**決めたこと**

| 場面 | どうするか |
|---|---|
| こちらで触っていない | **黙って取り込む。** 合流の必要が無い |
| 両方が触った・行が重ならない | 黙って合流する |
| 両方が触った・同じ行 | **git と同じ印**を入れて、人に決めてもらう |

自動で「正しい方」を選ばせない。**黙って間違えるのがいちばん怖い。**

**見張りの落とし穴: ファイル記述子だけでは足りない**

多くのエディタ（Claude Code を含む）は、上書き保存を
「別名で書いてから置き換える」形で行う。
**このときファイル記述子にはイベントが1つも飛んでこない。**
置き換わったのはディレクトリの項目であって、握っている中身ではないため。

親ディレクトリも見張る形にした。ただしディレクトリのイベントは
無関係なファイルの出入りでも飛ぶので、起こされるたびに `stat` を取り、
実体番号・更新時刻・大きさのどれかが変わったときだけ知らせる。

**`URLResourceValues` では差が出なかった**
`fileResourceIdentifier` の中身が不透明で、置き換えても「変わっていない」と判定され、
**何も知らせなくなった**。`stat` を直接使う形にした。
テストを先に書いていたので気づけた。

**競合扱いをどう外すか（ここが本丸）**

取り込んでも、それだけではダイアログが出続ける。
`NSDocument` が「最後に読み書きしたときのファイルの更新日時」を覚えていて、
保存時にディスクの値と突き合わせるため。

SwiftUI の `DocumentGroup` はこの値を公開していないが、実体を調べたところ
**ふつうの `NSDocument` の派生**（`FileWrapperPlatformDocument → PlatformDocument → NSDocument`）で、
`NSDocumentController.shared.documents` から取れた。**私有 API は要らない。**

```swift
document.fileModificationDate = ディスクの更新日時
document.updateChangeCount(.changeCleared)   // 取り込みのときだけ
```

合流したときは日付だけ合わせ、**変更の数え上げは戻さない**。
合流の結果はまだ保存されていない編集なので、戻すと未保存だと分からなくなる。

これが通ったので、`NSDocument` を自前で持つ作り直しは**不要**になった。

**順序**
本文の差し替えは SwiftUI 側の仕事で、書類の状態が追いつくのは次の周回。
同じ周回で後始末をすると上書きされる。`Task { @MainActor in … }` で1周ずらしている。

**縛ったこと**
合流の判断（`ExternalChangeResolver`）と突き合わせ（`ThreeWayMerge`）は
どちらも副作用を持たない関数にして、テストで縛った。
とくに「印を付けたとき、どちらの内容も消えていない」ことを重点的に見ている。

## D-24. エディタのハイライトを差分更新にする

**きっかけ**
1.8万文字の文書で「キーボードの反応が異常に遅い」と報告された。
文字数だけ見れば小さい（D-6 で「5万文字でも大丈夫」と判断していた）。

**測ったこと**（release / 1.8万文字・711行、打鍵1回ぶん）

| | 前 | 後 |
|---|---|---|
| 打鍵1回の合計 | **30.5 ms** | **3.6 ms** |
| トークン化 | 8.6 ms | 2.5 ms |
| 行の索引作り | 2.5 ms | 0.3 ms |
| 属性を貼る＋組み直し | 約 19 ms | 約 0.2 ms |

**原因は2つあった。**

### 1. 打鍵のたびに全文の属性を捨てて貼り直していた

`setAttributes` を文書全体にかけると、`NSTextStorage` は**その範囲のレイアウトを捨てる**。
貼る費用そのもの（2 ms）より、捨てられた組版を作り直す費用の方が大きい。

`MarkdownCore` は最初から「1行の解析は直前の行の状態だけで決まる」形にしてあり
（D-1）、差分更新を後から載せられる設計だった。その伏線を回収した。

- 編集された行から貼り直し、状態が前回と一致した行で打ち切る
- **編集した行の1行手前から**始める。表のヘッダは「次の行が区切り行か」でしか
  決まらないので（D-3）、ある行を直すと1行手前の見え方が変わる
- 貼らない行でも、ブロック状態とコードの色分けの状態は**必ず進める**。
  飛ばすと後ろの行の色が狂う

トークン化自体は全行やっている。2.5 ms なので、まずは十分。
ここが問題になったら、`tokenizeLine` を使った部分トークン化に進める。

### 2. `NSTextView.string` は NSString 由来で、走査が遅い

これが**効き幅としては同じくらい大きかった**。

| | NSString 由来 | 連続した記憶域に写してから |
|---|---|---|
| トークン化 | 8.6 ms | 2.5 ms |
| 行の索引作り | 2.5 ms | 0.3 ms |

1文字ずつ走査するたびに橋渡しの費用がかかる。
`makeContiguousUTF8()` で一度写せば 0.6 ms で済み、以降は Swift 側の速度で走る。

**教訓**
`String` は同じ型でも**中身の持ち方で速度が桁違いに変わる。**
AppKit / UIKit から受け取った文字列を、そのまま解析器に渡さないこと。

**縛ったこと**
差分の結果が全文貼り直しと**バイト単位で一致する**ことをテストにした
（`IncrementalHighlightTests`）。フェンスの開閉、表の区切り行、行の分割・削除、
連続入力など、状態が後ろへ伝播する編集を並べてある。
差分更新の事故は画面外で起きるので、目視では気づけない。

## D-23. プレビューのインラインコードは角丸の札にする

**決めたこと**
プレビューの `` `code` `` を、余白と角丸と枠線のある札として描く。
色も編集画面とは別に持つ（`inlineCodeText` / `inlineCodeBackground` / `inlineCodeBorder`）。
**編集画面は変えない。**

**理由**
記法文字が見えるかどうかで、必要な手がかりが違う。
編集画面にはバッククォートが残っているので、地の色を少しずらすだけでコードだと分かる。
プレビューは記法文字が消えるため、輪郭が無いとただの色付きの文字にしか見えない。

**`.backgroundColor` では作れない**
`NSAttributedString` の背景色は**角の無い矩形をそのまま塗る**。余白も付かない。
`NSLayoutManager` の `fillBackgroundRectArray` を差し替えて自分で描いている。
行をまたぐと矩形が複数渡るので、受け取った数だけ描く。

**余白は「札を広げる」のではなく「字送りを広げる」**

最初は矩形を左右に広げたが、**隣の字にかぶった。** 文字の位置は変わらないので当然だった。
`kern` で字送りの方を広げる形に変えた。

さらに**左の余白だけ、あとから潰れているのが分かった。**
矩形を左へ広げる作りだったため、行や表のマスの先頭では広げる余地が無く、
`max(0, x - padding)` で 0 になっていた。文中の札は正しく、先頭の札だけ詰まる。

直し方は、左の余白を**札の中に入れる**こと。幅ゼロの文字（U+2060 WORD JOINER）を
コードの頭に足し、その字送りを広げた。中の文字なので、行頭でも潰れようがない。

U+200B（ZERO WIDTH SPACE）ではなく U+2060 を使うのは、
前者が改行してよい位置と見なされ、札の頭だけが行末に残り得るため。

**測る側にも同じ処理を入れる**
表示用にだけ入れると、札のぶんだけ幅が足りず折り返しがずれる。
D-18（表の揃えを表示用と測定用で作り分けた件）と同じ形の落とし穴で、
**プレビューは属性文字列を2本作っている**ことを忘れると必ず踏む。

そのうえで、幅の測り方も変えることになった。
`NSAttributedString.size()` は**幅ゼロの文字の字送りを数えない。**
同じ文字列でも実際に組んだ幅より狭い値が返り、表の列が1文字ぶん足りずに折り返した。
高さと同じレイアウトマネージャで測る形に統一した。

**教訓**: 文字を足して見た目を作ると、測る経路も一緒に確かめる必要がある。
`size()` とレイアウトマネージャは別物で、常に一致するとは限らない。

**色を編集画面と共有しなかった理由**
同じ値にすると、片方を直したときにもう片方が黙って変わる。
役割が違うので名前を分けてある（`tableHeaderBackground` と同じ方針）。
別物であることはテストで縛った。

**枠線は両方に入れる。ただしダークは不透明にしない**
札の地とページ背景の差が、ライトは 1.06 しかない。枠線が無いと札の形が分からない。
ダークは地だけでも浮く（1.65）が、線を入れると縁が締まる。
不透明な白にすると線が主張しすぎるので、白の 22% にしてある。

**角は丸めすぎない**
カプセル状にすると、文中に置いたときボタンと見分けが付かなくなる。
文字サイズの 0.20 倍（14pt で 3pt）にとどめた。

## D-22. OS のアクセント／ハイライト色に従わない

**決めたこと**
利用者の OS 設定に追従していた2か所をやめ、配色表に取り込んだ。

| 場所 | 前 | 後 |
|---|---|---|
| ツールバーのボタン（目次・検索・プレビュー） | SwiftUI 既定＝OS のアクセントカラー | `.tint()` で `#FFD60A` に固定 |
| カーソル行の行番号 | `selectedContentBackgroundColor` | ライト `#7E6000` / ダーク `#FFD60A` |

併せて、目次の選択行（灰色 32%）とジャンプ先の点灯（橙）も黄色に揃えた。

**理由**
配色を1組に決めて全面で揃えているのに、ボタンの色だけ利用者の設定で変わる。
「この画面はこう見える」と言えなくなるし、スクリーンショットも人によって違う色で写る。

**気づいたきっかけ**
利用者のアクセントカラーが黄色で、**検索のヒットと同じ色に見えていた。**
実害は出ていなかったが、たまたま揃っていただけで、青に設定している人の環境では違う見え方になる。

**踏みかけた罠**

`#FFD60A` を**そのまま文字色に使えない。** ライトの背景（`#F5F5F5`）との比が 1.29 しかない。
黄色は明るいので、明るい地の上では文字として成立しない。
カーソル行の行番号はライトだけ暗い琥珀（`#7E6000`、比 5.41）にした。
これは B-10（OS のハイライト色を文字色に使って読めなかった）と同じ形の失敗で、
**システム色をやめても、色の性質そのものは変わらない。**

同じ理由で、半透明で重ねる色は**濃さを外観ごとに変えている。**
ジャンプ先の点灯を黄色にしたとき、ダークで同じ濃さにすると
白い文字とのコントラストが 3.3 まで落ちた。ライト 55% / ダーク 35% で 15.47 / 4.96。

**縛ったこと**
`controlAccentColor` などをそのまま使っていないこと、
カーソル行の行番号が背景に対して 4.5 以上あること、
点灯中でも見出しが読めること（合成後の色で測る）をテストにした。

## D-21. 文書内検索は自前で作り、置換は入れない

**決めたこと**
`NSTextView.usesFindBar` の標準の検索バーは使わず、SwiftUI で自前の帯を作った。
検索・ハイライト・件数・前後への送りまで。**置換は入れない。**

**標準の検索バーを捨てた理由**

| | 標準の Find Bar | 自前 |
|---|---|---|
| 実装量 | 1行（`usesFindBar = true`） | 1ファイル＋テーマの色3つ |
| 見た目 | OS 標準。`MarkdownTheme` に追従しない | 目次・プレビューと同じ帯に並ぶ |
| iOS 版 | `UITextView` に同じものが無く、別実装が要る | そのまま動く |

配色を1組に絞って全面で揃えているのに、検索の帯だけ系統の違う見た目が挟まる。
それを許すなら、そもそもテーマを持つ意味が薄い。

**置換を入れない理由**
「同じ語をまとめて直す」は、後から入れる**複数選択（⌘D）**の役目にする。
いま置換の UI を作ると、複数選択が入った時点で同じ用途の入り口が2つ並ぶ。

割り切ったのは**画面外まで含めた「すべて置換」**。複数選択では代替できないが、
必要になってから足す。

**持たせなかったもの**
大文字小文字の区別、単語単位、正規表現。判定は部分一致だけにした。
オプションが増えるほど「なぜ当たらないのか」の切り分けが要る。

**塗ることと移動することを分けた**

最初は「いま何番目か」が変わったらエディタが追う形にしていた。これだと
**検索の帯を出したまま本文を打つだけでカーソルが飛ぶ**。ヒットは打鍵のたびに
数え直されるので、数え直し＝移動の合図にしてはいけない。

塗るのは `SearchHighlight`（値を渡すだけ）、移動は `EditorSelectionRequest`
（`EditorScrollRequest` と同じく `id` を持つ依頼）に分けた。
前後へ送ったときと検索語を変えたときだけ依頼を出す。

**return は横取りしない**

前のヒットへ戻すのに ⇧return を当てようとして、`onKeyPress(keys: [.return])` を
検討したが**やめた**。日本語入力の変換確定まで奪う。
`onSubmit`（次のヒットへ）は AppKit が変換確定後にしか呼ばないので安全。
前へ戻るのは ⇧⌘G とボタンに任せた。

**ヒットの色は外観に追従させない**

最初はヒットの上の文字を本文の色（`text`）にしていた。するとダークでは
**白い文字を載せることになり、背景を暗く濁らせるほかなくなる**。
黄色が茶色になり、ダークでヒットが沈んで見えた。

文字の方を暗い色（`searchMatchText` = `#1C1C1E`）で固定し、
背景はライト・ダーク共通の明るい原色（`#FFD60A` / `#FF9500`）にした。
配色表の中でここだけ動的な色でないのは、この理由による。

**ハイライトは全文を貼り直す**
検索の色だけを剥がす手が無い（コードブロックの背景と `.backgroundColor` の
区別が付かない）。ハイライトは5万文字で 5.3 ms（D-6）なので、送るたびに走らせて間に合う。

**ヒットの上は文字色も差し替える**
背景だけ変えると、コードブロックの構文色（紫・緑）の上に黄色が来て読めない。
見出しの色もここで落ちるが、読めることを優先した。

**検索欄はヘッダー（ツールバー）に置く**

窓の幅いっぱいの帯を本文の上に挟む形から、ツールバーの 🔍 の左へ移した。
本文の表示面積を削らずに済み、目次・プレビューと操作の入り口が横一列に揃う。

ここで SwiftUI のツールバーに2度つまずいた。**どちらも「項目の増減」が原因。**

| 書き方 | 何が起きたか |
|---|---|
| `if showsSearch { ToolbarItem(...) }` | 項目が増減すると後続の項目を取り違える。**🔍 を押すとプレビューが消えた** |
| `ToolbarItem { Group { if showsSearch { ... } } }` | 中身が空のまま組まれた項目は、あとから中身を入れても現れない |

効いたのは、**常に同じ中身を置いて幅と不透明度だけ変える**書き方。

```swift
ToolbarItem(placement: .primaryAction) {
    searchField
        .frame(width: showsSearch ? nil : 0)
        .opacity(showsSearch ? 1 : 0)
        .disabled(!showsSearch)
        .clipped()
}
```

畳んでいるあいだ `disabled` にしてあるので、**出すのと同じ呼び出しの中で焦点を
指定しても効かない**（まだ無効）。`onChange(of: showsSearch)` で、描き直しの
あとに移している。

**教訓**: SwiftUI のツールバーは、項目の並びが変わることを前提にしていない。
出し入れしたいものは、項目ごと消すのではなく**中で畳む**。

**ヒットは「選択」しない**
選択の灰色が塗りを覆う（B-13）。カーソルを置くだけにしてある。

## D-20. 目次の選択は、OS のアクセント色を使わない

**症状**
目次で選んだ行が、窓が前面のときだけ OS のアクセント色（利用者の設定では黄色）で塗られた。
背面に回すと灰色に戻る。目次は「今どこを見ているか」を示すだけなので、色が強すぎる。

**`List(selection:)` を使うかぎり色は変えられない**
選択の塗りは `NSTableView` が描く。前面かどうかで
`selectedContentBackgroundColor` と `unemphasizedSelectedContentBackgroundColor` を
使い分けており、SwiftUI からこれを差し替える口は無い。

**対処**
`List(selection:)` をやめ、行を `Button`（`.buttonStyle(.plain)`）にして、
選ばれている行の背景を自分で描く。色は `theme.outlineSelection`
（記法の灰色 `marker` の 32%）。前面かどうかで変わらない。

`onTapGesture` ではなく `Button` にしたのは、キーボードや読み上げからも押せるため。

**検証で手こずったこと**

「クリックしたら選ばれるか」を確かめるのに、オフスクリーンの検証台では**再現できなかった**。
`swift run` で作った窓は key にならず（バンドルが無いため）、
合成したマウスイベントを SwiftUI が受け取らない。

実アプリで確かめようとしたが、**バイナリを直接起動しても書類の窓が開かない。**
`open` 経由で起動すると開く。環境変数は `--env`、標準エラーは `--stderr` で渡せる。

```sh
open -a <app> --env CLICK_TEST=1 --stderr /tmp/log.txt <file>
```

これで実アプリに合成クリックを送り、`[目次] 押された: コード 行=38` を確認できた。

**ついでに測ったこと**
SwiftUI が `AttributeGraph: cycle detected` を5件出すが、
**`List(selection:)` の頃から同じ5件**で、今回の変更で増えてはいない。

## D-19. ヘッダは列ごとに切らず、窓の幅いっぱいの帯にする

**症状**
目次・編集・プレビューと縦に3列に割れた画面で、**編集の列にだけヘッダの帯があり**、
目次とプレビューの列では消えていた。横一直線に見えない。

**最初の見立ては外していた**
目次の `listStyle` を `.sidebar` から `.inset` に変えた。これは的外れだった。
サイドバーの見た目は関係なく、**帯が途切れる理由はもっと構造的なところにあった。**
`.sidebar` には戻してある。

**測って分かったこと**

窓は `.fullSizeContentView` で開く（SwiftUI の既定）。この状態では
**`ScrollView` と `List` はタイトルバーの下まで伸びる。** 本文が下を流れる作りのため。
一方 `NSViewRepresentable` で載せたエディタは safe area を守って下から始まる。

3列を開いた状態で、各スクロールビューの上端を測った（タイトルバー 52pt）:

| 列 | 中身 | 上端 |
|---|---|---|
| 目次 | `List` | **0 pt**（潜っている） |
| 編集 | `NSScrollView` | **52 pt**（下から始まる） |
| プレビュー | `ScrollView` | **0 pt**（潜っている） |

タイトルバーは半透明なので、下に何があるかで見え方が変わる。
編集の列だけ下に何も無く、窓の地の色がそのまま帯として見えていた。

**対処**
窓から `.fullSizeContentView` を外す。本文はタイトルバーの下へ潜らなくなり、
3列とも 52pt から始まる。併せて `titlebarSeparatorStyle = .line` で境目に線を引く。

対処後に測り直した結果:

```
目次   ListCoreScrollView   上端から 52 pt
編集   NSScrollView         上端から 52 pt
プレビュー HostingScrollView    上端から 52 pt
NSTitlebarContainerView     上端から  0 pt  幅 1710（窓の全幅）
```

`NSWindow` の設定は SwiftUI から届かないので、
大きさゼロの `WindowConfigurator`（`NSViewRepresentable`）を1枚挟んで渡している。

**教訓（検証について）**

この環境では画面収録の権限が無く、タイトルバーを含む窓の描画は焼けない。

| 試した手 | 結果 |
|---|---|
| `NSThemeFrame` を `cacheDisplay` | SwiftUI の中身が透明のまま写らない |
| `frameView.layer?.render(in:)` | ほぼ全面が透明。ウインドウサーバ側で合成される部分は取れない |
| `NSHostingView` に目次だけ載せて焼く | 窓の文脈が無いので再現しない |

**絵が撮れないなら、寸法を測る。**
「どの列のスクロールビューが、上端から何 pt のところから始まっているか」を出したことで、
見た目を見なくても原因と直りが確定できた。
最初に見た目から原因を推測して外したのは、測る前に動いたため。

## D-18. 表は罫線で描く。揃えは段落スタイルに入れる

**やったこと**
プレビューの表を、罫線と見出し行のある普通の見た目にした。

**罫線の引き方**
線を1本ずつ引くのではなく、**マス目のあいだを 1pt 空けて、下地に罫線の色を敷く。**
各マスは不透明なので、空けたぶんだけが線として見える。

```swift
Grid(horizontalSpacing: 1, verticalSpacing: 1) { ... }
    .padding(1)                                  // 外周ぶん
    .background(Color(platform: theme.tableBorder))
```

線を個別に引くと、交点で太さがずれたり二重になったりする。こちらは交点が自動で揃う。

**ただしマスは行の高さいっぱいまで広げること。** 埋め残すと下地が面として見える（B-14）。

**見出し行の背景はコードブロックと同じ色**
`tableHeaderBackground` として別名を与えてある。いまは `codeBackground` と同じ値だが、
役割が違うので名前を分けた（どちらかだけ変えたくなったときに困らない）。

**揃えが効いていなかった**

`| ---: |` と書いても右寄せにならなかった。原因は揃えの入れ場所。

プレビューの本文は `NSTextView` で描いており（D-14）、**提案された幅いっぱいに広がる**。
そのため外側の `frame(maxWidth: .infinity, alignment: .trailing)` では、
テキストビュー自体が右端まで伸びるだけで、中の文字は左のままだった。

揃えは**段落スタイル**（`NSMutableParagraphStyle.alignment`）に入れて解決した。

**ただし測る側には入れない**
中央・右揃えにすると、グリフがコンテナ幅いっぱいに配置され、
測った幅が実際の文字幅より広くなる。表示用と測定用で属性文字列を作り分けた。

| 用途 | 揃え |
|---|---|
| 画面に出す方（`textStorage`） | 列の指定どおり |
| 幅と高さを測る方（`measuringStorage`） | 常に `.natural` |

`PreviewAttributes.make(alignment:)` の既定は `.natural`。
測定側がうっかり揃えを受け取らないよう、既定でも縛ってある（テストあり）。

**教訓**
「引数はあるのに使われていない」は動かして初めて分かる。
`PreviewText` は前から `alignment` を受け取っていたが、
AppKit の経路だけ無視していた（iOS の `Text` では効いていた）。
**プラットフォームごとに実装が分かれている引数は、両方の経路で確かめる。**

## D-17. フッターの行数は、行番号と同じ数え方にする

**やったこと**
窓の下端に細い帯を置き、右寄せで「テーマ・文字サイズ・行数・大きさ」を出す。

**文字コードは出さない**
読み書きとも UTF-8 に固定していて選べない。選べないものを表示しても判断の材料にならない。
（将来 Shift_JIS の読み込みに対応するなら、そのとき足す）

**見つかった食い違い**
作った直後、**行番号は 14 までなのにフッターは 15 行**と出た。

原因は末尾の改行の後ろの空行。`layoutManager.enumerateLineFragments` は
この行を渡してこない（グリフが1つも無いため）。一方 `LineIndex` は1行として数える。

カーソルは置けるのだから行として存在する。行番号側を直した。

```swift
// 末尾が改行のとき、その後ろの空行は enumerateLineFragments に出てこない
if layoutManager.extraLineFragmentTextContainer != nil {
    drawNumber(lineIndex.lineCount, in: layoutManager.extraLineFragmentUsedRect)
}
```

数え方が2か所に分かれてしまうため、`DocumentSize.lineCount` と `LineIndex.lineCount` が
常に一致することをテストで縛った（`StatusBarTests`）。

**大きさは UTF-8 のバイト数**
文字数ではなく、保存したときのファイルの大きさと一致させる。
日本語は1文字3バイトなので、文字数で数えていると気づかないままずれる。

**教訓**
同じものを2か所で数え始めたら、**その2つが一致することをテストにする。**
今回は目で見て気づけたが、長い文書では気づけなかった。

## D-16. 行番号はテキストビューの左余白に描く

**やったこと**
編集画面の左端に行番号を出す。設定画面のスイッチで消せる。プレビューには出さない。

**選択肢**

| 案 | 評価 |
|---|---|
| 本文の左に `NSTextView` をもう1枚並べ、スクロールを同期させる | 却下。スクロール位置・行の高さ・折り返しを自分で合わせ続けることになる |
| `NSScrollView` の定規（`NSRulerView`）として付ける | 最初はこれを採用したが、**あとで取りやめた**。定規があると AppKit がタイトルバーに縦線を引く（B-11） |
| **テキストビューの左余白を広げ、`drawBackground(in:)` で描く** | **採用。番号が本文と同じ座標系に乗るので、位置合わせもスクロール追従も AppKit 任せ** |

番号は本文と同じ座標系にあるので、行の位置は `usedRect` に
`textContainerOrigin` を足すだけで求まる。スクロールしてもテキストビューごと
動くため、追従のためのコードが要らない。

**折り返した行に番号を振らない**
`layoutManager.enumerateLineFragments` は折り返しでできた断片も1つずつ渡してくる。
そのまま番号を振ると、折り返すたびに番号が増えてしまう。
断片の先頭が論理行の先頭と一致するときだけ描くことで避けた。
判定には目次と同じ `LineIndex`（行頭位置の索引）をそのまま使えた。

```swift
let characterIndex = layoutManager.characterIndexForGlyph(at: fragmentGlyphRange.location)
let line = lineIndex.line(atUTF16Offset: characterIndex)
guard lineIndex.utf16Offset(ofLine: line) == characterIndex else { return }  // 折り返しの続き
```

**幅は桁数で決める**
1000 行を超えたときに数字が切れないよう、`lineCount` の桁数から帯の幅を計算し、
`textContainerInset.width` に反映する。

**iOS では作らない**
`UITextView` の `drawBackground(in:)` に相当する差し込み口が無い。
ファイルごと `#if canImport(AppKit)` で囲った。iOS で行番号を出すときは別の作りになる。

## D-15. 目次はパーサに手を入れずに作れた

**やったこと**
左端に見出しの目次を出す。階層表示、開閉、クリックでその行へ移動。

**`MarkdownCore` には一切触っていない**

必要な材料はすべてトークンから取れた。

| 欲しかったもの | どのトークンから取ったか |
|---|---|
| 見出しのレベル | `.heading(level:)` |
| 見出しの行番号 | `tokenizeLines` の並び順 |
| 記法を除いた文字列 | 見出しの範囲から `.marker` と `.linkURL` の範囲を差し引く |

`# **設計** の話` → 「設計 の話」、`# [参考](https://example.com)` → 「参考」。
**トークンが範囲を持っている**ことが、そのまま効いた（[D-1](#d-1-エディタのハイライトはトークン列にするast-にしない)）。

**開閉は「畳んだものだけ覚える」**

`List(children:)` は既定で畳まれた状態から始まる。目次は全体を見渡すためのものなので、
開く操作から始めさせたくない。`DisclosureGroup` を自分で並べ、
**畳んだ項目の id だけ**を `Set` に持つ形にした。

開いた方を覚える作りにすると、編集で見出しが増えたときに新しい項目が畳まれた状態で出てくる。
畳んだ方を覚えれば、増えた項目は自然に開いた状態になる。

**崩れた文書への備え**

`#` の次が `####` のようにレベルが飛ぶ、いきなり `###` から始まる、
といった文書でも階層が壊れないようにした。テストで固めてある。
コードブロックの中の `# 偽物` は、トークナイザが見出しにしないので自動的に除外される。

**エディタへの移動**

`EditorScrollRequest` を新設した。行番号そのものではなく
**依頼が新しく発行されたか**で判定したいので、値に `UUID` を持たせて
同じ行を続けて選んでも別の値になるようにしている。

## D-14. プレビューの本文は AppKit の `NSTextView` で描く

**きっかけ**
リンクの下線・指マークカーソル・ホバー効果の3つが欲しい。
SwiftUI の `Text` では[どれも実現できない](#d-13-プレビューのリンクはホバーで下線ではなく常に下線)。

**採った案**
プレビューの本文（見出し・段落・表のセル）を `NSTextView` で描く。
`NSTextView` は `.link` 属性があれば**指マークのカーソルとクリックでの URL 起動**を
自前で面倒みてくれる。下線は `linkTextAttributes`、ホバーは追跡領域で自分で書く。

iOS では従来どおり SwiftUI の `Text`（`#if canImport(AppKit)` で分岐）。
ホバーという概念が無いので不足しない。

**意味づけの置き場所は変えていない**
`PreviewModel` は装飾を `inlinePresentationIntent` に載せたまま。
`PreviewAttributes` がそれを AppKit の属性へ落とす。
**意味づけを1か所に置き、描画側が解釈する**という形を保っている。

**表示と測定でレイアウトを分ける**

最初は、表示に使っている `NSTextView` のレイアウトをそのまま測定にも使っていた。
大きさを測るたびにコンテナの幅を書き換えるため、**表示側の折り返し幅が測定時の値に引きずられる**。
`layout()` で毎回ビュー幅へ戻す作りにしたが、これが不安定だった。

> **`layout()` は呼ばれる保証がない。**
> SwiftUI がフレームを設定しても `needsLayout` が立たなければ呼ばれない。

症状は「起動後の最初のリサイズだけ折り返さない、2回目以降は正常、
しばらく静止するとまた戻る」という再現しにくいもので、
同期が成立したりしなかったりする状態と一致していた。

**対処: 測定を完全に別立てにした。**

```
表示用: NSTextView が自分の幅に追従（widthTracksTextView = true。AppKit 標準）
測定用: 別の NSTextStorage / NSLayoutManager / NSTextContainer で高さだけ計算
```

測定は表示側のコンテナに触れないので、手で同期する必要が無くなった。
**同期漏れという失敗の形そのものが消える。**
測定用のレイアウトマネージャは `allowsNonContiguousLayout = false`（推定値が返る余地を消す）。

**リサイズ中の負荷**

`PreviewText` の `body` の中で属性文字列を作っていた。
`body` は再描画のたびに評価されるため、リサイズ中は毎フレーム全ブロックを作り直す。

| | 毎フレーム（5,544文字 / 60ブロック） |
|---|---|
| 修正前 | 1.51 ms（うち属性変換 1.50 ms） |
| 修正後 | 0.01 ms |

変換を `Coordinator` に移し、本文・文字サイズ・テーマが変わったときだけ作り直す。
これを直すまで、リサイズ中はエディタ側の描画まで押し出されていた。

**AppKit を SwiftUI のレイアウトに混ぜて壊れた箇所**

いずれも「AppKit のビューは SwiftUI が期待する情報を持たない」ことに起因する。

| 症状 | 原因 | 対処 |
|---|---|---|
| 表が潰れた | `Grid` が列幅を決める段階では幅が提案されない。0 として扱っていた | 幅未指定なら「折り返さない自然な幅」を返す |
| リストのマーカーがずれた | AppKit のビューはベースラインを持たない | `alignmentGuide(.firstTextBaseline)` にフォントの ascender を渡す |
| 全体が 10,000pt に膨張 | 幅未指定時に巨大なコンテナで測ったら、`usedRect` が**コンテナ幅をそのまま返した**（520 なら正しく 153 を返すのに、10,000 なら 10,000 を返す） | `NSAttributedString.size()` で自然な幅を直接測る |
| 長文が折り返さない | `sizeThatFits` は異なる幅で何度も呼ばれ、コンテナに最後の値が残る。**測った幅と表示する幅がずれていた** | `layout()` でコンテナの幅を必ずビューの幅に合わせる |
| リスト項目だけ狭く折り返す | 理想の幅が大きすぎて `HStack` が配分しきれない | 中身に `frame(maxWidth: .infinity)` |
| `HSplitView` の中で折り返さない | `HSplitView` は子に確定した幅を提案しないことがある。リサイズ中だけ折り返し、止めると戻る | `GeometryReader` で幅を実測して明示的に渡す |

**教訓**
`NSViewRepresentable` でテキストを描くときは、
**「測るときの幅」と「描くときの幅」が一致しているか**を最初に疑う。
`sizeThatFits` は1回しか呼ばれないと思い込まないこと。

原因が分からなかったものは、`sizeThatFits` の戻り値を出力して初めて掴めた。
推測で直そうとせず、実際の値を見ること。

**検証環境は本番と同じ形にすること。**
確認用のハーネスが `.frame(width:)` で幅を固定していたため、
実際のアプリで起きる「幅が提案されない」状況を再現できていなかった。
`HSplitView` を含む構造に直して、ようやく手元で再現した。

**失ったもの**
ブロックをまたぐテキスト選択。段落ごとの選択になった。

## D-13. プレビューのリンクは「ホバーで下線」ではなく「常に下線」

**やりたかったこと**
プレビューでリンクにマウスを乗せたとき、下線を出す。

**できなかった理由**

SwiftUI の `Text` は**リンク単位のホバーを扱えない**。

| 調べたこと | 結果 |
|---|---|
| `onHover` | **ビュー単位のみ**。`Text` の中の特定のリンクには付けられない |
| リンク用のホバー API（`linkHover` など） | 存在しない |
| `TextRenderer`（カスタム描画） | macOS 15 以降。いずれにせよホバーは扱えない |

実現するには、プレビューの本文描画を `Text` から `NSTextView` に置き換えることになる。
150〜250行、macOS 専用（iOS 版で別途実装が必要）、
テキスト選択・行送り・スクロール同期の挙動も変わる。**割に合わない。**

**採った案: 常に下線を引く**

`AttributedString` に `underlineStyle` を載せるだけ。1行で済み、iOS でも同じように動く。
多くの Markdown ビューアがこの方式。エディタ側で URL に下線を引いているのとも揃う。

対象は3種類すべて。`[text](url)` / 裸の URL / メールアドレス。
`linkifyBareURLs` の側にも同じ指定が要る（`NSDataDetector` で後から張るリンクのため）。

## D-12. コードブロックのシンタックスハイライトは自前の最小実装にする

**やりたいこと**
コードブロックの中身を言語ごとに色分けする。いまは `code` 色の単色。

**候補（2026-08-07 時点の実測）**

| | Splash | Highlightr | 自前で最小実装 |
|---|---|---|---|
| 作者 | John Sundell | raspu | — |
| 対応言語 | **Swift のみ** | 190以上（highlight.js 内蔵） | 決めた分だけ |
| 実装量 | 純 Swift 2,195行 | Swift 1,500行 + highlight.js | 200行程度 |
| 同梱リソース | **168 KB** | **2.1 MB**（js 1.0MB + テーマ 271種） | 0 |
| 実行方式 | ネイティブ | **JavaScriptCore で JS を実行** | ネイティブ |

参考: アプリの実行ファイルは 4.6 MB（Release）。

**判断: 外部ライブラリは使わず、自前で4分類だけ実装した**

- Highlightr は 2.1 MB を同梱し、コードブロックごとに JS エンジンを呼ぶ。
  「可能な限り軽く」という方針と正面から衝突する
- Splash は Swift 専用。汎用の Markdown エディタとしては中途半端
- 4分類（キーワード・文字列・コメント・数値）なら約 280 行、依存ゼロで足りる

**実装**（`NullnoteUI/CodeSyntax.swift`）

```
MarkdownCore の .codeBlock / .codeLanguage
    ↓
CodeSyntax で言語ごとに走査
    ↓
キーワード / 文字列 / コメント / 数値 に色を付ける
```

`MarkdownCore` には手を入れていない。「UI 非依存」は守られている。
エディタとプレビューで同じトークナイザを使う。

対応言語: swift / javascript(ts, jsx, tsx) / python / php / bash(sh, zsh) / ruby /
C系(c, cpp, java, kotlin, go, rust, csharp) / json / sql / yaml(toml, ini)。
言語指定なし・未知の言語は色分けしない。

**設計の判断**

- **行をまたぐブロックコメント**に対応するため、`State` を行間で引き継ぐ形にした。
  これが無いと `/* ... */` の途中の行だけ色が外れる
- **コードブロックの地の色を `code`（ピンク）から `text` に変えた。**
  ピンクのままだと構文の色が沈んで見える。インラインコードはピンクのまま
- SQL だけ `ignoresKeywordCase` を立てた。`SELECT` も `select` もキーワード

**割り切ったこと**

型名と変数名の区別、関数呼び出しの検出はしない。
VS Code のような細かさが要るようになったら、そのとき Highlightr を検討する。

**テスト**（`CodeSyntaxTests`、15件）

間違えやすい箇所を明示的に固めた。

- `letter` は `let` で始まるがキーワードではない
- `"a\"b"` のエスケープされた引用符で文字列を終わらせない
- 文字列やコメントの中のキーワードは拾わない
- `utf8` の `8` を数値として拾わない

## D-11. テーマ切り替えは「配色を2組持つ」のではなく「解決先を上書きする」

**決めたこと**
配色は1組だけ持つ。色はすべて外観に追従する動的な色として定義し、
`MarkdownTheme.appearance`（`.system` / `.light` / `.dark`）が
どちらで解決するかを上書きする。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| ライト用とダーク用の配色を2組持つ | 片方だけ直して食い違う事故が起きやすい。色の定義が2倍になる |
| 外観ごとに属性文字列を貼り直す | 動的な色は描画時に解決されるので、そもそも貼り直す必要が無い |

**実装**

| 指定 | AppKit | UIKit | SwiftUI |
|---|---|---|---|
| `.system` | `appearance = nil`（親から受け継ぐ） | `.unspecified` | `preferredColorScheme(nil)` |
| `.light` | `NSAppearance(named: .aqua)` | `.light` | `.light` |
| `.dark` | `NSAppearance(named: .darkAqua)` | `.dark` | `.dark` |

エディタ側は `NSScrollView` に外観を設定する。中の `NSTextView` は親から受け継ぐので、
設定箇所が1つで済む。

**例外**
プレビューのインラインコードだけは、解析時にフォントと色を焼き込んでいる
（[B-2](#b-2-プレビューの取り消し線とインラインコードが見た目に出ない) の対処の副作用）。
そのため外観が変わったときは組み直す。`MarkdownPreview` の `task(id:)` のキーに
`appearance` を含めてある。

**検証**
ホスト側をライト外観にしたまま、テーマだけダーク指定して描画し、
背景の明るさが 1.00 → 0.17 に変わることを確認した（逆方向も同様）。
「親の外観に引きずられていないこと」まで確かめないと、上書きが効いた証明にならない。

## D-10. スクロール同期は行番号で対応付ける

**決めたこと**
エディタの表示範囲の先頭にある行番号を求め、プレビュー側でその行を含むブロックを
画面上端に合わせる。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| スクロール量を比率で配分 | エディタとプレビューで行の高さが違う（見出しの拡大、コードブロックの余白、表の罫線）。下へ行くほどずれが積み上がる |
| ブロックの実測位置を測って補間 | 正確だが、SwiftUI の `ScrollView` に任意のオフセットを与える手段が macOS 14 に無い。`ScrollPosition` は macOS 15 以降 |
| 最低 OS を macOS 15 に上げる | 上の案のためだけに対応 OS を切るのは割に合わない |

**実装**

```
エディタ                                      プレビュー
NSTextView.characterIndexForInsertion(at:)     PreviewBlock.sourceLine
  → LineIndex で行番号へ                        （swift-markdown の SourceRange 由来）
  → topVisibleLine (Binding<Int>)  ──────────→  blockID(containing:) → ScrollViewReader
```

`characterIndexForInsertion(at:)` を使ったのは、TextKit 1 と TextKit 2 の
どちらで動いていても同じ答えが返るため。レイアウトマネージャに直接触ると、
どちらで動いているかを気にすることになる。

**割り切ったこと**

- ブロック単位でしか合わない（長い段落の途中では、その段落の先頭で止まる）
- エディタ → プレビューの一方向のみ。逆方向も入れるとスクロールの取り合いになる

仕様に「大幅にずれてしまう場合は、同期をキャンセルしてよい」とあるが、
ブロックに吸着させる方式なので、そもそも大きくずれることがない。

**ついでに直したこと**
`updateNSView` で `textView.string != text` と比較していた。
`NSTextView.string` は呼ぶたびに文字列を作り直すため、スクロールのたびに
本文全体をコピーすることになっていた。Coordinator 側に控えを持って比較するよう変更。

### B-15. ⌘F を押しても検索欄に焦点が移らない

**症状**
⌘F で検索欄は出るが、**カーソルは本文に残ったまま**。そのまま打つと本文に入る。

**原因**
`@FocusState` と `focused(_:)` は書いてあったが、効かなかった。
**SwiftUI の焦点はツールバーの項目まで届かない。**
ツールバーは本文とは別の階層（`NSTitlebarContainerView`）に載るため、
本文側の焦点の輪の中に入っていない。

**対処**
AppKit の側から渡す。入力欄の隣に大きさゼロのビューを1枚置き、
そこから親をたどって `NSTextField` を探し、`window.makeFirstResponder` を呼ぶ
（`SearchFieldFocuser`）。⌘F のたびに合図の値を増やして発火させる。

窓の全体から探さないのは、ツールバーが別の階層にいるため。
自分の位置から親をたどる方が確実で、段数も区切れる。

**閉じたときも同じ問題が起きる**
閉じただけでは焦点が宙に浮き、打っても本文に入らない。
`EditorFocusRequest`（ほかの依頼と同じ形）を出して、編集画面に焦点を返している。
カーソルは検索で降りた場所のまま。そこから続けて直せる。

**教訓**
`@FocusState` は同じ焦点の輪の中でしか効かない。
ツールバー・シート・別の窓など、**階層をまたぐ焦点は AppKit で確かめること。**

### B-14. 表に、太い灰色の帯が出ることがある

**症状**
プレビューの表に、行の途中や列の一部だけ**太い灰色の帯**が出る。
出る表と出ない表があり、窓の幅によっても変わる。

**原因**
表は「マス目のあいだを 1pt 空け、下地に罫線の色を敷く」作りにしてある（D-18）。
帯の正体は**その下地**で、マスに覆われていない部分がそのまま見えていた。

`Grid` は行の高さを一番高いマスに合わせるが、**マスの方を引き伸ばさない**。
`alignment: .topLeading` なので背の低いマスは上に寄り、下に隙間が残る。

だから次の2つで出る。

| 出る条件 | 見え方 |
|---|---|
| 空のマス（`\| 最低 OS \| macOS 14.0 \| \|`） | その列だけ帯 |
| 隣のマスが折り返して2行になった行 | 折り返していない列に帯 |

「表による」「窓の幅による」のはこのため。

**修正**
マスに `frame(maxHeight: .infinity)` を足し、行の高さいっぱいまで広げた。

**教訓**
**隙間を下地の色で見せる作りは、上に載せるものが必ず隙間を埋めることが前提。**
1つでも埋め残すと、罫線ではなく面として出る。
`Grid` の `alignment` は「余った空間のどこに置くか」であって、
「埋めるかどうか」は別に指定する必要がある。

### B-13. 検索の「いま見ているヒット」が灰色になる

**症状**
検索でヒットした語は黄色に塗れているのに、**いま見ている1件だけ灰色**になる。
ダークではとくに見分けが付かない。

**原因**
前後へ送るときに、そのヒットを `setSelectedRange` で**選択**していた。
検索欄に入力の焦点があるあいだテキストビューは非アクティブなので、AppKit は
選択範囲を `unemphasizedSelectedTextBackgroundColor`（灰色）で塗る。
しかもこれは**属性の背景色より後に描かれる**ので、指定した橙色が完全に隠れる。

**修正**
範囲を選ぶのをやめ、**先頭に長さ 0 のカーソルを置く**だけにした
（`Coordinator.reveal(_:)`）。塗りは出ず、帯を閉じたあとそのまま編集も続けられる。

**教訓**
`NSTextView` の描画は「属性 → 選択 → カーソル」の順に重なる。
属性で色を決めても、その上に AppKit が描くものがある。
**選択は装飾ではなく状態**であって、見た目の指定と混ぜてはいけない。

### B-12. 「システム」に戻すと、今度はプレビューだけライトのまま残る

**症状**
ライト → システムに切り替えると、エディタはダークになるのに
**プレビューの背景とフッターだけライトのまま**。OS はダーク。

B-8 と同じ形だが、残る場所が入れ替わっている。

**なぜ半分だけ直っていたか**

| 描いているもの | 色の決まり方 | B-8 のあと |
|---|---|---|
| エディタ、プレビューの本文（AppKit） | `view.appearance` に**具体的な外観**を設定 | 直っていた |
| プレビューの背景、フッター、目次（SwiftUI） | `Color(nsColor:)` を SwiftUI の `colorScheme` で解決 | **直っていなかった** |

B-8 では AppKit 側だけ「nil を渡さない」ようにしていた。
SwiftUI 側は `preferredColorScheme(theme.appearance.colorScheme)` のままで、
`.system` では nil を渡していた。

**nil は「システムに合わせ直せ」ではない**

`preferredColorScheme(nil)` は「好みなし」。一度ライトを明示したあとに nil へ戻しても、
SwiftUI 側の配色は**ライトのまま残る**。ウインドウの実効外観は正しく戻っているのに、
`Color` の解決だけ古いままになる。

```
③ システムに戻した直後
  window.effective = NSAppearanceNameDarkAqua   ← 正しい
  プレビューの背景  = #F5F5F5                    ← ライトのまま
```

**切り分け**
利用者の操作（起動 → ライト → システム）を再現する検証台を作り、
各段階で窓を PNG に焼いて、エディタ・プレビュー・フッターの背景色を比べた。

| 試したこと | 結果 |
|---|---|
| `MarkdownPreview` と `OutlineView` の重複した `preferredColorScheme` を外す | **直らない**（重複は原因ではない） |
| `.system` を具体的な `ColorScheme` に解決してから渡す | **直る** |

**対処**
`preferredColorScheme` を直に呼ばず、`View.markdownColorScheme(_:)` を通す。
`.system` は `NSApp.effectiveAppearance` から具体的な配色へ解決する。

```swift
case .system: SystemAppearance.current   // .light か .dark。nil は返さない
```

**具体的に解決したら、OS の変化は自分で拾う**
配色を固定した以上、OS 側でライト／ダークが切り替わっても自動では追従しない。
`NSApp.effectiveAppearance` を KVO で見張る `SystemAppearance` を置いた。
`NSApp.appearance` は SwiftUI が触らない（ウインドウ側だけ書き換える）ので、
ここが変わるのは OS の設定が変わったときだけ。

検証台では5段階すべてで3つの領域の配色が一致した（起動 → ライト → システム → OS ライト → OS ダーク）。

**再発しにくくしたこと**
nil を返す `MarkdownAppearance.colorScheme` は**削除した**。
残しておくと、また誰かが `preferredColorScheme` に直接渡す。

**教訓**
同じ原因の不具合は、**同じ形をした場所を全部洗う**。
B-8 のとき「AppKit に nil を渡すな」で直した気になったが、
本質は「外観の指定に nil（＝継承・好みなし）を使うな」で、
SwiftUI 側にも同じ穴が空いていた。

### B-11. 定規を付けると、AppKit がタイトルバーに縦線を引く

**症状**
行番号の区切り線が、閉じるボタンの脇を通ってタイトルバーの中まで伸びる。
ライトでもダークでも同じ。

**まず自分を疑ったが、違った**
`drawHashMarksAndLabels(in:)` は自分の `bounds` に閉じ込めてある（B-9）。
計測でも定規はタイトルバーの下に収まっていた。

```
ruler→window       = (0, 0, 30, 791)
contentLayoutRect  = (0, 0, 1061, 791)   ← タイトルバーを除いた領域と一致
window.frame.height = 843                ← 上の 52pt がタイトルバー
```

**切り分け**
アプリ自身に `NSThemeFrame` を `cacheDisplay` させて PNG に焼き、画素を数えた。
（この環境では画面収録の権限が無く、スクリーンショットが撮れないため）

| 試したこと | タイトルバーの縦線 |
|---|---|
| 区切り線をマゼンタにする | 色が変わらない → **自分の線ではない** |
| 定規の幅を 30pt 広げる | 線も一緒に移動（x=29pt → 59pt）→ **定規に追従している** |
| 行番号を消す（定規を外す） | **消える** |
| `window.titlebarSeparatorStyle = .none` | 消えない |
| ツールバーの項目一覧を確認 | 分離子（tracking separator）は入っていない |

`NSScrollView` に定規があると、AppKit が定規の右端をなぞる線を
タイトルバー（`_NSTitlebarDecorationView` の領域）まで引く。公開の設定では消せなかった。

**対処: `NSRulerView` をやめる**

| 案 | 結果 |
|---|---|
| スクロールビューに自前のビューを足し、`contentInsets` で本文を右へずらす | **失敗。** SwiftUI がまだ大きさを決めていない時点で `contentInsets` を入れると、テキストコンテナの幅が 7pt まで潰れて本文が消えた（D-14 と同じ罠） |
| **テキストビューの左右の余白（`textContainerInset`）を広げ、`drawBackground(in:)` で左側へ描く** | **採用** |

番号が本文と同じ座標系に乗るので、スクロールへの追従も行の位置合わせも
AppKit 任せで済む。`usedRect` に `textContainerOrigin` を足すだけになった。

**代償**: `textContainerInset.width` は左右に等しく効くので、右の余白も
同じだけ広がる（12pt → 42pt）。テキストコンテナの幅の決め方に触れずに済むので、
折り返しの追従を壊さないことを優先した。

**教訓**
「線が出ている」と「その線を自分が描いた」は別のこと。
**色を変えて、動かして、消してみる。** 三つとも一致して初めて犯人が確定する。
最初の計測（`convert(bounds, to: nil)`）は正しかったのに、
症状と噛み合わないので疑ってしまった。計測が正しいときは、前提の方が間違っている。

**細かい落とし穴**: `NSView.enclosingScrollView` は、スクロールビューの
**直接の子では `nil` を返す**（クリップビューの中に居ることを前提にしている）。
`superview` は `NSScrollView` なのに `nil`、という食い違いで一度止まった。

### B-10. 「システムのハイライト色」を文字色に使うと読めない

**やろうとしたこと**
カーソルのある行の番号を、OS のハイライトカラー設定の色で太字にする。

**素直に実装すると失敗する**
ハイライトカラーそのものは `NSColor.selectedTextBackgroundColor` だが、
これは**選択範囲の背景**用に明度を上げてある色で、文字色には向かない。
利用者の設定（黄色）で実測した値:

| 色 | ライト | ダーク |
|---|---|---|
| `selectedTextBackgroundColor`（ハイライト色そのもの） | `#FFEEBE` | `#8B7A3F` |
| `selectedContentBackgroundColor`（選択項目の背景色） | `#E1AC15` | `#D19E00` |
| `controlAccentColor` | `#FFC726` | `#FFC600` |

ライトの背景 `#F5F5F5` に対するコントラスト比は、
`selectedTextBackgroundColor` が **1.43**、`selectedContentBackgroundColor` が **1.90**。
前者は太字にしても背景に埋もれて読めなかった（画像で確認）。

**採用**
`selectedContentBackgroundColor` を文字色に使う。同じハイライト／アクセント設定から
導かれる色なので、利用者が黄色以外に変えれば追従する点は変わらない。

**「見分けが付くか」を明度で測ってはいけない**
ふつうの行番号は灰色 `#A8AAB2`。琥珀色 `#E1AC15` との**コントラスト比は 1.12** しかない。
明るさが近いだけで、実際は色相で明確に区別できる。
回帰テストは彩度で見るようにした（灰色は彩度ほぼ 0、強調色は 0.9 前後）。

**焦点の出入りを知る手段が AppKit に無い**
ファーストレスポンダが変わったことを伝える通知は存在しない。
`NSTextView` を継承して `becomeFirstResponder()` / `resignFirstResponder()` を
拾う `FocusReportingTextView` を作った。

`window?.firstResponder` を見に行かないのは、`becomeFirstResponder()` の時点では
ウインドウ側がまだ更新されておらず、古い答えが返るため。自分で状態を持つ。

テキストビューは `NSTextView.scrollableTextView()` が作ったものを差し替えているが、
**TextKit 一式（テキストストレージ、レイアウトマネージャ、テキストコンテナ）は引き継ぐ**。
自分で組み直すと折り返しやスクロールの設定を作り直すことになり、
過去に何度も踏んだ落とし穴（D-14 のプレビュー）に戻る。

**描き直しの合図**

| きっかけ | 拾い方 |
|---|---|
| カーソルが動いた | `textViewDidChangeSelection(_:)` |
| 焦点が出入りした | `FocusReportingTextView.onFocusChange` |
| スクロールした | `boundsDidChangeNotification`（既存） |
| 本文が変わった | `textDidChange(_:)`（既存） |

### B-9. 行番号を出すと本文が消える

**症状**
行番号は正しく出るのに、本文の領域が単色に塗りつぶされてテキストが見えなくなる。

**切り分け**
オフスクリーンに焼いた PNG の色数を数えて、どこまでが正常かを1段ずつ確かめた。

| 状態 | 本文域の色数 |
|---|---|
| 定規なし | 822 |
| 定規を付けるが、何も描かない | 822 |
| 定規を付け、背景だけ塗る | **1** |
| 定規を付け、全部描く | **1** |

「付けるだけ」なら無事で「背景を塗ると」消える。犯人は描画の1行目だと確定した。

**原因**
`drawHashMarksAndLabels(in rect:)` に渡る `rect` を、定規の描画範囲だと思い込んでいた。
実際の値を出すと **スクロールビュー全体の大きさ** だった。

```
bounds = (0, 0,  31, 560)   ← 定規の幅
rect   = (0, 0, 520, 560)   ← 渡ってきた矩形。本文の上まで含む
```

`rect.fill()` が本文の上まで塗りつぶしていた。

**対処**
塗る範囲を必ず自分の `bounds` に閉じ込める。

```swift
let area = bounds.intersection(rect)
guard !area.isEmpty else { return }
theme.background.setFill()
area.fill()
```

**教訓**
描画メソッドに渡る矩形は「描いてよい範囲」ではなく「描き直しが要る範囲」であり、
自分の領域より広いことがある。**塗りつぶす前に自分の `bounds` と交差させる。**

回帰テストは `NSBitmapImageRep` に描かせて、定規の外の画素が
番兵の色のまま残っているかを見る形にした（`LineNumberGutterTests`）。
`area.fill()` を `rect.fill()` に戻すと落ちることも確かめてある。

**ついでに直したこと**
`Coordinator.appliedAppearanceName`（B-8 で足したもの）が `#if canImport(AppKit)` の
外に出ていて、iOS 向けビルドが通らなくなっていた。iOS ビルドは
`xcodebuild -destination 'generic/platform=iOS'` を回さないと気づけない。

### B-8. 「システム」に戻すと、エディタだけ前のテーマのまま残る

**症状**
ライト → システムに切り替えると、ヘッダーは暗くなるのに編集画面は白いまま。
クリックなど何か操作すると暗くなる。ダーク → システムでは起きない
（結果が同じなので気づけないだけ）。

**原因**
`.system` のときに `appearance = nil`（＝親から継承）を設定していた。
**AppKit は「明示指定 → 継承」に戻したとき、実効外観を下位のビューへ伝えない。**

実際の値（OS はダーク、ライト → システムに切り替えた直後）:

```
hosting.appearance    = nil(継承)  実効=DarkAqua   ← 正しく更新された
scrollView.appearance = nil(継承)  実効=Aqua       ← 古いまま
textView.appearance   = nil(継承)  実効=Aqua       ← 古いまま
```

`appearance` は正しく `nil` になっているのに、**実効外観だけが取り残される**。

**効かなかった手当て**（実測）

| 試したこと | 結果 |
|---|---|
| `viewDidChangeEffectiveAppearance()` を呼ぶ | 変わらず |
| 親の実効外観を入れてから `nil` に戻す | 変わらず |
| `documentView` を付け直す | 変わらず |
| **`NSApp.effectiveAppearance` を明示** | **直った** |

**対処**
`MarkdownAppearance.platformAppearance` を **`NSAppearance?` から `NSAppearance` に変えた。**
`.system` のときは `NSApp.effectiveAppearance` へ自分で解決する。**`nil` は返さない。**

副作用として、OS 側でテーマが変わったときに追従させる必要が出た。
`@Environment(\.colorScheme)` を読むことで SwiftUI の更新を受け、
比較も「解決後の外観の名前」で行うようにした（`.system` のままでも OS が変われば貼り直す）。

**教訓**
**「継承させる」は、状態を戻す操作としては信用できない。**
明示的な値を入れ続ける方が、どのビューがどの状態かを追える。
D-14 で「同期漏れという失敗の形そのものを無くす」と書いたのと同じ話だった。

推測で直そうとせず、`appearance` と `effectiveAppearance` を両方出力して初めて掴めた。

### B-7. 開いた直後だけハイライトが付かない

**症状**
ファイルを開いた直後は本文が単色。どこかを編集すると色が付く。

**原因**
`makeNSView` の中で、ハイライトを適用した**あとに**テーマを適用していた。

```swift
// 誤り
textView.string = text
highlight(...)                 // 装飾を貼る
apply(theme, to: scrollView)   // textView.textColor が全体を塗り潰す ❌
```

`NSTextView.textColor` と `font` は **本文全体**を一括で塗り替える。
ハイライトのあとに設定すると装飾が消える。
編集すると `textDidChange` で再ハイライトが走るので、そこで色が戻っていた。

**対処**
`makeNSView` を「テーマ → 本文 → ハイライト」の順に直した。
`updateNSView` と iOS 側（`makeUIView`）は元から正しい順序だった。

**混入した経緯**
テーマ切り替えを入れたとき、`apply` の引数を `textView` から `scrollView` へ変える際に
呼び出し位置も動かしてしまった。引数の変更に気を取られ、順序への影響を見落とした。

**再発防止**
`EditorSetupOrderTests` を追加。正しい順序で見出しが `heading` 色になることに加え、
**誤った順序だと本文色になってしまう挙動そのものをテストに書いた**。
「なぜこの順序でなければならないか」をコードに残すため。

**教訓**
属性を貼る処理と、ビュー全体の見た目を設定する処理は、**順序に依存する**。
後者が前者を破壊する側なので、必ず先に済ませること。

### B-6. ウインドウの角丸は変えられない（調査して結論、変更なし）

**きっかけ**
ウインドウの四隅が Chrome より丸く見える、という指摘。

**調べたこと**

| | 結果 |
|---|---|
| Nullnote と Chrome のビルド SDK | 両方とも macOS 26.5。SDK の違いではない |
| `NSWindow` の角丸を指定する API | AppKit のヘッダに存在しない |
| 旧デザインへ戻す Info.plist キー | 見つからず（`UIDesignRequiresCompatibility` は iOS 向け） |
| Chrome の `NSPrincipalClass` | `BrowserCrApplication` = 自前でウインドウを描いている |

**結論**
macOS 26 では標準ウインドウの角丸はシステムが決める。アプリからは指定できない。
Chrome が違って見えるのは、システムの枠を使わず自前で描いているため。

テキストエディットと並べて確認したところ、Nullnote と同じだった。**変更不要。**

**変えるとしたら**
枠なしウインドウにして、信号機ボタン・リサイズ・影・タイトルバーを自前実装することになる。
標準の挙動（フルスクリーン、タブ、ウインドウ復元）の一部を失い、
OS 更新でデザインが変わったときに自前部分だけ取り残される。**やらない。**

### B-5. ダークテーマでチェックマークが暗く沈む

**症状**
チェック済みのチェックボックスが、ライトでは白いチェック、ダークでは暗いチェックになる。

**原因**
`checkmark.square.fill` は**チェック部分を塗らずに背景を透かす**描き方。
単色で描くと、透けた先の色がそのままチェックの色になる。

| | 透ける先 | 見え方 |
|---|---|---|
| ライト | `#F5F5F5` | 白いチェック |
| ダーク | `#293238` | 暗いチェック ← これ |

**対処**

```swift
Image(systemName: "checkmark.square.fill")
    .symbolRenderingMode(.palette)
    .foregroundStyle(.white, Color(platform: theme.accent))
```

自前で図形を重ねる案（`RoundedRectangle` + `checkmark`）も同じ見た目になったが、
SF Symbol のままにした。文字とのベースライン合わせや、文字サイズ変更への追従を
自前で持たずに済むため。

**教訓**
`.fill` 系のシンボルは「塗り」ではなく「抜き」で形を作っているものがある。
**16pt では違いが分からなかった。60pt で描いて初めて見えた。**
色の検証は拡大して行うこと。

### B-4. 「保存先ディレクトリが選べない」— アプリの不具合ではなかった

**報告された症状**
「名前」だけ編集でき、「タグ」は入力できず、「場所」はグレーアウトして鍵アイコンが出る。

**真因**
押していたのは **⇧⌘S**。macOS の書類アプリでは、これは「別名で保存」ではなく **「複製」**。

メニューの実際の割り当て（`AXMenuItemCmdModifiers` を読んで確認）:

| 項目 | 割り当て |
|---|---|
| 保存 | ⌘S |
| **複製** | **⇧⌘S** |
| 別名で保存… | ⌥⇧⌘S |

（`閉じる = ⌘W` / `すべてを閉じる = ⌥⌘W` と一致するので、この読み取りは正しい）

複製された書類はまだディスク上に無いので、名前は付けられても**場所とタグは無効**になる。
ウインドウ名が「roundtrip のコピー2」だったのが決定的な証拠だった。

**Windows / Adobe 系では ⇧⌘S が Save As なので、間違えやすい。**

**入れた対処**
原因とは別に、保存パネルを既定で展開表示にした（`AppSettings.registerDefaults()` で
`NSNavPanelExpandedStateForSaveMode` を登録）。折りたたみ状態だと保存先が
「場所」ポップアップだけになるので、最初からファイルブラウザが開くようにした。
`register` なので、ユーザーが自分で畳めばその選択が優先される。

**⇧⌘S を「別名で保存」に付け替えなかった理由**
SwiftUI で付け替えるには `CommandGroup(replacing: .saveItem)` で
保存グループ全体を差し替え、保存・別名で保存・複製を自前で実装し直すことになる。
プラットフォームの慣習に逆らううえ、得るものが釣り合わない。

**調べて分かった副産物**

- `net.daringfireball.markdown` は LaunchServices に正しく登録されている
- サンドボックスアプリの保存パネルは別プロセス（`openAndSavePanelService`）で動くため、
  アプリ側の AX ツリーには中身が出ない。System Events では中を調べられない

**教訓**
UI の見た目から原因を推測して回るより、**メニューの実際のキー割り当てを読む**方が速かった。
「どの操作をしたか」を最初に確定させること。

## 検証方法についての記録

この環境では画面収録とアクセシビリティの権限が無く、
`screencapture` と `osascript` のキー操作送信が使えなかった。

**代わりに使った手段**

| 確認したいこと | 手段 |
|---|---|
| ビューの見た目 | `NSTextView` / `NSHostingView` をオフスクリーンで PNG に焼く |
| アプリ自身の窓の中身 | アプリに `NSThemeFrame` を `cacheDisplay` させて書き出す（B-11 で使用） |
| 窓やビューの寸法 | アプリにビュー階層を歩かせて、ウインドウ座標で書き出す（D-19 で使用） |
| クリックしたときの挙動 | `open --env` でアプリを起こし、中から合成イベントを送る（D-20 で使用） |
| アプリが起動したか | `pgrep` |
| ファイルを開けたか | System Events でウインドウタイトルを読む |
| メニュー構成 | System Events でメニュー項目名を読む |

**保存の検証について**
文字入力を伴う操作が自動化できず長らく未検証だったが、
利用者が実際に ⌥⇧⌘S で `~/Desktop/Sample.md` へ保存した形跡
（`NSOSPLastRootDirectory = "~/Desktop"` と実ファイル）で確認できた。
UI を動かせないときは、**アプリが残した痕跡を読む**方が早いことがある。

**注意**: System Events の `enabled` プロパティは、メニューを開く前は
標準項目まで `false` と報告する。有効・無効の判定には使えない。

**アプリの起こし方**
バイナリを直接叩くと書類の窓が開かない。`open` 経由なら開く。
環境変数は `--env`、標準エラーは `--stderr` で渡せる。

```sh
open -a <app> --env KEY=1 --stderr /tmp/log.txt <file>
```

**焼けないもの**（D-19 で判明）
タイトルバー・ツールバー・サイドバーの材質は、`cacheDisplay` でも
`layer.render(in:)` でも取れない。ウインドウサーバ側で合成されるため。
ウインドウの装飾に関わる修正は、利用者に目で見て確かめてもらうしかない。
