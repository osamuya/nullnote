# 判断の記録

なぜこの作りになったか。**後から読んで「なぜこうしなかったのか」に答えられる**ことを目的とする。
構成そのものは [`../README.md`](../README.md) に、各層の詳細は各パッケージの README にある。

## D-1. エディタのハイライトはトークン列にする（AST にしない）

**決めたこと**
`MarkdownCore` は「ソース上の範囲 + 種別」の平たい列だけを返す。ネストしたドキュメント木は持たない。

**理由**
エディタが必要とするのは `NSTextStorage` に属性を貼るための範囲だけ。
打鍵ごとに再計算するので、軽さが正義。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| AST を持つ | 実装量と再計算コストが上がる。エディタに木構造は要らない |
| `AttributedString(markdown:)` を使う | 範囲情報が取れず、記法文字を薄く表示するといった制御ができない |

**代償**
プレビューの描画には使えない。→ [D-4](#d-4-プレビューは-swift-markdown-で描く) で別パーサを立てることになった。

**副産物**
1行の解析が「直前の行の状態」だけで決まる形にしたので、差分更新を後から載せられる。
`MarkdownBlockState` は 6 通りしかない。

## D-2. トークンは重なることを許す

**決めたこと**
`# **見出し**` は見出しトークンと強調トークンの両方を生む。
配列は**外側が内側より先**に並ぶ。

**理由**
重なりを禁じると、生成側が範囲を分割する処理を持つことになり複雑になる。
一方、属性の適用は配列順に貼れば内側が外側を上書きして自然に正しくなる。

**気をつけること**
配列を位置順にソートし直すとこの保証が壊れる。
太字・斜体は「上書き」ではなく「足す」必要がある（`PlatformFont.addingTraits`）。

## D-3. 対応記法は CommonMark 基本 → 後から GFM 拡張を追加

**経緯**
当初は CommonMark 基本セットのみで実装。後から GFM 拡張が必要と判明して追加した。

**追加時に設計を変えずに済んだ点 / 済まなかった点**

| | 影響 |
|---|---|
| 取り消し線・タスクリスト | トークン種別を足すだけ。設計変更なし |
| 拡張オートリンク | インライン走査に分岐を足すだけ |
| **表** | **公開 API の変更が必要になった** |

表のヘッダ行は「次の行が列数の一致する区切り行である」ことでしか判別できない。
そのため `tokenizeLine` に `nextLine:` を足して1行だけ先読みする形にした。

```swift
tokenizeLine(text, range:, stateBefore:, nextLine:)
```

後ろ向きの参照は入れていないので、差分更新の打ち切り判定（`stateAfter` の収束）は成立したまま。

**教訓**
「対応記法の範囲」は着手前に確定させておくべきだった。データモデルには影響しなかったが、
API の形は変わった。

## D-4. プレビューは swift-markdown で描く

**決めたこと**
`apple/swift-markdown`（cmark-gfm のラッパ）を `NullnoteUI` の依存に追加し、
AST から SwiftUI ビューを組む。

**理由**
GFM の表を含む準拠した解析がタダで手に入る。プレビューは打鍵ごとには走らないので速度要件が緩い。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| `AttributedString(markdown:)` | **表を表現できない**。GFM 対応を決めた時点で不可 |
| cmark-gfm → HTML → `WKWebView` | CSS でテーマを作れるが、テーマの二重管理と WebView の起動コストが付く |
| 自前レンダラ | 依存ゼロだが実装量が大きい。得るものが釣り合わない |

**守った境界**
依存は `NullnoteUI` 止まり。`MarkdownCore` は Foundation のみのまま。
エディタのハイライト経路に外部依存は入っていない。

## D-5. 裸の URL は `NSDataDetector` で補う

**問題**
swift-markdown が有効にしている cmark 拡張は `table` / `strikethrough` / `tasklist` の3つだけで、
**`autolink` は有効になっていない**。一方 `MarkdownCore` は裸の URL をリンクとして着色する。
このままエディタとプレビューで見え方がずれる。

```
Sources/Markdown/Parser/CommonMarkConverter.swift:624-626
    cmark_parser_attach_syntax_extension(parser, cmark_find_syntax_extension("table"));
    cmark_parser_attach_syntax_extension(parser, cmark_find_syntax_extension("strikethrough"));
    cmark_parser_attach_syntax_extension(parser, cmark_find_syntax_extension("tasklist"));
```

**決めたこと**
`PreviewModel` 側で `NSDataDetector` を使って後から補う。

**注意点**
`NSDataDetector` は GFM より貪欲で、`example.com` 単体も拾ってしまう。
`MarkdownCore` と同じ条件（`http://` `https://` `www.` またはアットマークを含む）まで絞り込んでいる。
両者の判定条件がずれると、また見え方が食い違う。

## D-6. プレビューはデバウンスする（同期パースにしない）

**測ったこと**（release ビルド / Apple Silicon）

| 文字数 | `MarkdownTokenizer.tokenize` | `PreviewBuilder.build` |
|---|---|---|
| 500 | 0.06 ms | 0.47 ms |
| 1万 | 1.0 ms | 9.2 ms |
| 5万 | **5.3 ms** | **45.7 ms** |

**判断**

- **プレビュー**: 5万文字で 45.7 ms。1フレーム（16.7 ms）の約3倍なので、
  `body` 内での同期パースは不可。入力が止まって 150 ms 後に解析する
  （`task(id:)` は値が変わると前のタスクを取り消すので、先頭で待つだけでデバウンスになる）。
- **エディタ**: 5万文字で 5.3 ms。1フレームに収まるので、打鍵ごとに全文を貼り直して問題ない。
  **差分更新は実装しない。** 必要になってから入れる（設計上は載る形にしてある）。

**教訓**
「重そうだから最適化する」ではなく、測ってから決める。
エディタ側は測った結果、最適化が**不要**と分かった。

## D-7. `.xcodeproj` は手書きし、ファイル同期グループを使う

**決めたこと**
`project.pbxproj` を手で書いた。`Nullnote/` は `PBXFileSystemSynchronizedRootGroup`。

**理由**
Xcode GUI を使わずにプロジェクトを作る必要があった。
Xcode 16 以降のファイル同期グループなら、**ディスクにファイルを置くだけでターゲットに入る**ため、
`.swift` を1つ足すたびに pbxproj を編集する必要がない。

**構成上の工夫**
`Info.plist` と `.entitlements` は同期グループの外（`Supporting/`）に置いた。
同期グループの中に入れると、リソースとしてコピーされる恐れがあるため。

**注意**
pbxproj の ID は 24桁の16進。手書きするなら重複しない規則を決めておくこと
（このプロジェクトは `AA00000000000000000000xx`）。

## D-8. 日本語ロケールを宣言する

**問題**
自作のメニュー項目は日本語なのに、標準メニューが「File」「Edit」のまま出て混ざっていた。

**原因**
アプリが対応ロケールを宣言していないと、AppKit は標準メニューを英語で出す。

**対処**
`Info.plist` に `CFBundleDevelopmentRegion = ja` と `CFBundleLocalizations = [ja, en]`、
pbxproj の `developmentRegion` を `ja` に。
→ 「ファイル」「編集」「表示」「ウインドウ」「ヘルプ」になった。

## D-9. サンドボックスは最初から有効にする

**決めたこと**
`com.apple.security.app-sandbox` と `files.user-selected.read-write` を最初から入れた。

**理由**
App Store 配布の必須要件。後から有効にすると、それまで通っていたファイルアクセスが
軒並み止まって直すのが大変になる。

**現状**
署名はローカル実行用のアドホック。配布時に Developer ID / App Store の証明書へ差し替える。
そのとき `com.apple.security.get-task-allow`（デバッガ接続用）が残っていないか確認すること。

## 実装中に見つけた不具合

記録として残す。同種の間違いを繰り返さないため。

### B-1. `~~~b~~~` が取り消し線として誤解析される

チルダ3連続を「フェンス記号だから取り消し線ではない」と弾いた後、
**1文字だけ進めて同じ連続の内側から数え直していた**ため、
`~~` + `b~` + `~~` と解釈されていた。

**修正**: 弾くときは連続全体を読み飛ばす（`InlineScanner.appendStrikethrough`）。

**教訓**: 「条件に合わないので nil を返す」と「消費せずに次へ」は違う。
走査位置を進める量まで含めて考える。

### B-2. プレビューの取り消し線とインラインコードが見た目に出ない

`inlinePresentationIntent` に `.strikethrough` / `.code` を載せていたが描画されなかった。
**SwiftUI の `Text` が実際に描くのは強調と強い強調だけ。**

**修正**: 意味づけとは別に、具体的な属性（`strikethroughStyle`、`font`）も指定する。

**副作用**: インラインコードのフォントに解析時点の文字サイズが焼き込まれるため、
文字サイズが変わったときもプレビューを組み直す必要が生じた
（`MarkdownPreview` の `task(id:)` のキーに `fontSize` を含めた）。

**教訓**: 「意味づけを載せれば描いてくれるはず」を信じない。目で見て確かめる。

### B-3. `ImageRenderer` では `task` が走らない

オフスクリーン描画で確認しようとしたら、プレビューが真っ白になった。
`ImageRenderer` はビューのライフサイクルを回さないため、`task` 内の解析が実行されない。

**対処**: `NSHostingView` をウインドウに載せ、ランループを回してから `cacheDisplay(in:to:)` する。

**教訓**: 非同期に中身を組むビューは、同期的にスナップショットできない。
印刷や画像書き出しを実装するときも同じ問題が出る。

## D-17. フッターの行数は、行番号と同じ数え方にする

**やったこと**
窓の下端に細い帯を置き、右寄せで「テーマ・文字サイズ・行数・大きさ」を出す。

**文字コードは出さない**
読み書きとも UTF-8 に固定していて選べない。選べないものを表示しても判断の材料にならない。
（将来 Shift_JIS の読み込みに対応するなら、そのとき足す）

**見つかった食い違い**
作った直後、**行番号は 14 までなのにフッターは 15 行**と出た。

原因は末尾の改行の後ろの空行。`layoutManager.enumerateLineFragments` は
この行を渡してこない（グリフが1つも無いため）。一方 `LineIndex` は1行として数える。

カーソルは置けるのだから行として存在する。行番号側を直した。

```swift
// 末尾が改行のとき、その後ろの空行は enumerateLineFragments に出てこない
if layoutManager.extraLineFragmentTextContainer != nil {
    drawNumber(lineIndex.lineCount, in: layoutManager.extraLineFragmentUsedRect)
}
```

数え方が2か所に分かれてしまうため、`DocumentSize.lineCount` と `LineIndex.lineCount` が
常に一致することをテストで縛った（`StatusBarTests`）。

**大きさは UTF-8 のバイト数**
文字数ではなく、保存したときのファイルの大きさと一致させる。
日本語は1文字3バイトなので、文字数で数えていると気づかないままずれる。

**教訓**
同じものを2か所で数え始めたら、**その2つが一致することをテストにする。**
今回は目で見て気づけたが、長い文書では気づけなかった。

## D-16. 行番号はテキストビューの左余白に描く

**やったこと**
編集画面の左端に行番号を出す。設定画面のスイッチで消せる。プレビューには出さない。

**選択肢**

| 案 | 評価 |
|---|---|
| 本文の左に `NSTextView` をもう1枚並べ、スクロールを同期させる | 却下。スクロール位置・行の高さ・折り返しを自分で合わせ続けることになる |
| `NSScrollView` の定規（`NSRulerView`）として付ける | 最初はこれを採用したが、**あとで取りやめた**。定規があると AppKit がタイトルバーに縦線を引く（B-11） |
| **テキストビューの左余白を広げ、`drawBackground(in:)` で描く** | **採用。番号が本文と同じ座標系に乗るので、位置合わせもスクロール追従も AppKit 任せ** |

番号は本文と同じ座標系にあるので、行の位置は `usedRect` に
`textContainerOrigin` を足すだけで求まる。スクロールしてもテキストビューごと
動くため、追従のためのコードが要らない。

**折り返した行に番号を振らない**
`layoutManager.enumerateLineFragments` は折り返しでできた断片も1つずつ渡してくる。
そのまま番号を振ると、折り返すたびに番号が増えてしまう。
断片の先頭が論理行の先頭と一致するときだけ描くことで避けた。
判定には目次と同じ `LineIndex`（行頭位置の索引）をそのまま使えた。

```swift
let characterIndex = layoutManager.characterIndexForGlyph(at: fragmentGlyphRange.location)
let line = lineIndex.line(atUTF16Offset: characterIndex)
guard lineIndex.utf16Offset(ofLine: line) == characterIndex else { return }  // 折り返しの続き
```

**幅は桁数で決める**
1000 行を超えたときに数字が切れないよう、`lineCount` の桁数から帯の幅を計算し、
`textContainerInset.width` に反映する。

**iOS では作らない**
`UITextView` の `drawBackground(in:)` に相当する差し込み口が無い。
ファイルごと `#if canImport(AppKit)` で囲った。iOS で行番号を出すときは別の作りになる。

## D-15. 目次はパーサに手を入れずに作れた

**やったこと**
左端に見出しの目次を出す。階層表示、開閉、クリックでその行へ移動。

**`MarkdownCore` には一切触っていない**

必要な材料はすべてトークンから取れた。

| 欲しかったもの | どのトークンから取ったか |
|---|---|
| 見出しのレベル | `.heading(level:)` |
| 見出しの行番号 | `tokenizeLines` の並び順 |
| 記法を除いた文字列 | 見出しの範囲から `.marker` と `.linkURL` の範囲を差し引く |

`# **設計** の話` → 「設計 の話」、`# [参考](https://example.com)` → 「参考」。
**トークンが範囲を持っている**ことが、そのまま効いた（[D-1](#d-1-エディタのハイライトはトークン列にするast-にしない)）。

**開閉は「畳んだものだけ覚える」**

`List(children:)` は既定で畳まれた状態から始まる。目次は全体を見渡すためのものなので、
開く操作から始めさせたくない。`DisclosureGroup` を自分で並べ、
**畳んだ項目の id だけ**を `Set` に持つ形にした。

開いた方を覚える作りにすると、編集で見出しが増えたときに新しい項目が畳まれた状態で出てくる。
畳んだ方を覚えれば、増えた項目は自然に開いた状態になる。

**崩れた文書への備え**

`#` の次が `####` のようにレベルが飛ぶ、いきなり `###` から始まる、
といった文書でも階層が壊れないようにした。テストで固めてある。
コードブロックの中の `# 偽物` は、トークナイザが見出しにしないので自動的に除外される。

**エディタへの移動**

`EditorScrollRequest` を新設した。行番号そのものではなく
**依頼が新しく発行されたか**で判定したいので、値に `UUID` を持たせて
同じ行を続けて選んでも別の値になるようにしている。

## D-14. プレビューの本文は AppKit の `NSTextView` で描く

**きっかけ**
リンクの下線・指マークカーソル・ホバー効果の3つが欲しい。
SwiftUI の `Text` では[どれも実現できない](#d-13-プレビューのリンクはホバーで下線ではなく常に下線)。

**採った案**
プレビューの本文（見出し・段落・表のセル）を `NSTextView` で描く。
`NSTextView` は `.link` 属性があれば**指マークのカーソルとクリックでの URL 起動**を
自前で面倒みてくれる。下線は `linkTextAttributes`、ホバーは追跡領域で自分で書く。

iOS では従来どおり SwiftUI の `Text`（`#if canImport(AppKit)` で分岐）。
ホバーという概念が無いので不足しない。

**意味づけの置き場所は変えていない**
`PreviewModel` は装飾を `inlinePresentationIntent` に載せたまま。
`PreviewAttributes` がそれを AppKit の属性へ落とす。
**意味づけを1か所に置き、描画側が解釈する**という形を保っている。

**表示と測定でレイアウトを分ける**

最初は、表示に使っている `NSTextView` のレイアウトをそのまま測定にも使っていた。
大きさを測るたびにコンテナの幅を書き換えるため、**表示側の折り返し幅が測定時の値に引きずられる**。
`layout()` で毎回ビュー幅へ戻す作りにしたが、これが不安定だった。

> **`layout()` は呼ばれる保証がない。**
> SwiftUI がフレームを設定しても `needsLayout` が立たなければ呼ばれない。

症状は「起動後の最初のリサイズだけ折り返さない、2回目以降は正常、
しばらく静止するとまた戻る」という再現しにくいもので、
同期が成立したりしなかったりする状態と一致していた。

**対処: 測定を完全に別立てにした。**

```
表示用: NSTextView が自分の幅に追従（widthTracksTextView = true。AppKit 標準）
測定用: 別の NSTextStorage / NSLayoutManager / NSTextContainer で高さだけ計算
```

測定は表示側のコンテナに触れないので、手で同期する必要が無くなった。
**同期漏れという失敗の形そのものが消える。**
測定用のレイアウトマネージャは `allowsNonContiguousLayout = false`（推定値が返る余地を消す）。

**リサイズ中の負荷**

`PreviewText` の `body` の中で属性文字列を作っていた。
`body` は再描画のたびに評価されるため、リサイズ中は毎フレーム全ブロックを作り直す。

| | 毎フレーム（5,544文字 / 60ブロック） |
|---|---|
| 修正前 | 1.51 ms（うち属性変換 1.50 ms） |
| 修正後 | 0.01 ms |

変換を `Coordinator` に移し、本文・文字サイズ・テーマが変わったときだけ作り直す。
これを直すまで、リサイズ中はエディタ側の描画まで押し出されていた。

**AppKit を SwiftUI のレイアウトに混ぜて壊れた箇所**

いずれも「AppKit のビューは SwiftUI が期待する情報を持たない」ことに起因する。

| 症状 | 原因 | 対処 |
|---|---|---|
| 表が潰れた | `Grid` が列幅を決める段階では幅が提案されない。0 として扱っていた | 幅未指定なら「折り返さない自然な幅」を返す |
| リストのマーカーがずれた | AppKit のビューはベースラインを持たない | `alignmentGuide(.firstTextBaseline)` にフォントの ascender を渡す |
| 全体が 10,000pt に膨張 | 幅未指定時に巨大なコンテナで測ったら、`usedRect` が**コンテナ幅をそのまま返した**（520 なら正しく 153 を返すのに、10,000 なら 10,000 を返す） | `NSAttributedString.size()` で自然な幅を直接測る |
| 長文が折り返さない | `sizeThatFits` は異なる幅で何度も呼ばれ、コンテナに最後の値が残る。**測った幅と表示する幅がずれていた** | `layout()` でコンテナの幅を必ずビューの幅に合わせる |
| リスト項目だけ狭く折り返す | 理想の幅が大きすぎて `HStack` が配分しきれない | 中身に `frame(maxWidth: .infinity)` |
| `HSplitView` の中で折り返さない | `HSplitView` は子に確定した幅を提案しないことがある。リサイズ中だけ折り返し、止めると戻る | `GeometryReader` で幅を実測して明示的に渡す |

**教訓**
`NSViewRepresentable` でテキストを描くときは、
**「測るときの幅」と「描くときの幅」が一致しているか**を最初に疑う。
`sizeThatFits` は1回しか呼ばれないと思い込まないこと。

原因が分からなかったものは、`sizeThatFits` の戻り値を出力して初めて掴めた。
推測で直そうとせず、実際の値を見ること。

**検証環境は本番と同じ形にすること。**
確認用のハーネスが `.frame(width:)` で幅を固定していたため、
実際のアプリで起きる「幅が提案されない」状況を再現できていなかった。
`HSplitView` を含む構造に直して、ようやく手元で再現した。

**失ったもの**
ブロックをまたぐテキスト選択。段落ごとの選択になった。

## D-13. プレビューのリンクは「ホバーで下線」ではなく「常に下線」

**やりたかったこと**
プレビューでリンクにマウスを乗せたとき、下線を出す。

**できなかった理由**

SwiftUI の `Text` は**リンク単位のホバーを扱えない**。

| 調べたこと | 結果 |
|---|---|
| `onHover` | **ビュー単位のみ**。`Text` の中の特定のリンクには付けられない |
| リンク用のホバー API（`linkHover` など） | 存在しない |
| `TextRenderer`（カスタム描画） | macOS 15 以降。いずれにせよホバーは扱えない |

実現するには、プレビューの本文描画を `Text` から `NSTextView` に置き換えることになる。
150〜250行、macOS 専用（iOS 版で別途実装が必要）、
テキスト選択・行送り・スクロール同期の挙動も変わる。**割に合わない。**

**採った案: 常に下線を引く**

`AttributedString` に `underlineStyle` を載せるだけ。1行で済み、iOS でも同じように動く。
多くの Markdown ビューアがこの方式。エディタ側で URL に下線を引いているのとも揃う。

対象は3種類すべて。`[text](url)` / 裸の URL / メールアドレス。
`linkifyBareURLs` の側にも同じ指定が要る（`NSDataDetector` で後から張るリンクのため）。

## D-12. コードブロックのシンタックスハイライトは自前の最小実装にする

**やりたいこと**
コードブロックの中身を言語ごとに色分けする。いまは `code` 色の単色。

**候補（2026-08-07 時点の実測）**

| | Splash | Highlightr | 自前で最小実装 |
|---|---|---|---|
| 作者 | John Sundell | raspu | — |
| 対応言語 | **Swift のみ** | 190以上（highlight.js 内蔵） | 決めた分だけ |
| 実装量 | 純 Swift 2,195行 | Swift 1,500行 + highlight.js | 200行程度 |
| 同梱リソース | **168 KB** | **2.1 MB**（js 1.0MB + テーマ 271種） | 0 |
| 実行方式 | ネイティブ | **JavaScriptCore で JS を実行** | ネイティブ |

参考: アプリの実行ファイルは 4.6 MB（Release）。

**判断: 外部ライブラリは使わず、自前で4分類だけ実装した**

- Highlightr は 2.1 MB を同梱し、コードブロックごとに JS エンジンを呼ぶ。
  「可能な限り軽く」という方針と正面から衝突する
- Splash は Swift 専用。汎用の Markdown エディタとしては中途半端
- 4分類（キーワード・文字列・コメント・数値）なら約 280 行、依存ゼロで足りる

**実装**（`NullnoteUI/CodeSyntax.swift`）

```
MarkdownCore の .codeBlock / .codeLanguage
    ↓
CodeSyntax で言語ごとに走査
    ↓
キーワード / 文字列 / コメント / 数値 に色を付ける
```

`MarkdownCore` には手を入れていない。「UI 非依存」は守られている。
エディタとプレビューで同じトークナイザを使う。

対応言語: swift / javascript(ts, jsx, tsx) / python / php / bash(sh, zsh) / ruby /
C系(c, cpp, java, kotlin, go, rust, csharp) / json / sql / yaml(toml, ini)。
言語指定なし・未知の言語は色分けしない。

**設計の判断**

- **行をまたぐブロックコメント**に対応するため、`State` を行間で引き継ぐ形にした。
  これが無いと `/* ... */` の途中の行だけ色が外れる
- **コードブロックの地の色を `code`（ピンク）から `text` に変えた。**
  ピンクのままだと構文の色が沈んで見える。インラインコードはピンクのまま
- SQL だけ `ignoresKeywordCase` を立てた。`SELECT` も `select` もキーワード

**割り切ったこと**

型名と変数名の区別、関数呼び出しの検出はしない。
VS Code のような細かさが要るようになったら、そのとき Highlightr を検討する。

**テスト**（`CodeSyntaxTests`、15件）

間違えやすい箇所を明示的に固めた。

- `letter` は `let` で始まるがキーワードではない
- `"a\"b"` のエスケープされた引用符で文字列を終わらせない
- 文字列やコメントの中のキーワードは拾わない
- `utf8` の `8` を数値として拾わない

## D-11. テーマ切り替えは「配色を2組持つ」のではなく「解決先を上書きする」

**決めたこと**
配色は1組だけ持つ。色はすべて外観に追従する動的な色として定義し、
`MarkdownTheme.appearance`（`.system` / `.light` / `.dark`）が
どちらで解決するかを上書きする。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| ライト用とダーク用の配色を2組持つ | 片方だけ直して食い違う事故が起きやすい。色の定義が2倍になる |
| 外観ごとに属性文字列を貼り直す | 動的な色は描画時に解決されるので、そもそも貼り直す必要が無い |

**実装**

| 指定 | AppKit | UIKit | SwiftUI |
|---|---|---|---|
| `.system` | `appearance = nil`（親から受け継ぐ） | `.unspecified` | `preferredColorScheme(nil)` |
| `.light` | `NSAppearance(named: .aqua)` | `.light` | `.light` |
| `.dark` | `NSAppearance(named: .darkAqua)` | `.dark` | `.dark` |

エディタ側は `NSScrollView` に外観を設定する。中の `NSTextView` は親から受け継ぐので、
設定箇所が1つで済む。

**例外**
プレビューのインラインコードだけは、解析時にフォントと色を焼き込んでいる
（[B-2](#b-2-プレビューの取り消し線とインラインコードが見た目に出ない) の対処の副作用）。
そのため外観が変わったときは組み直す。`MarkdownPreview` の `task(id:)` のキーに
`appearance` を含めてある。

**検証**
ホスト側をライト外観にしたまま、テーマだけダーク指定して描画し、
背景の明るさが 1.00 → 0.17 に変わることを確認した（逆方向も同様）。
「親の外観に引きずられていないこと」まで確かめないと、上書きが効いた証明にならない。

## D-10. スクロール同期は行番号で対応付ける

**決めたこと**
エディタの表示範囲の先頭にある行番号を求め、プレビュー側でその行を含むブロックを
画面上端に合わせる。

**捨てた案**

| 案 | 捨てた理由 |
|---|---|
| スクロール量を比率で配分 | エディタとプレビューで行の高さが違う（見出しの拡大、コードブロックの余白、表の罫線）。下へ行くほどずれが積み上がる |
| ブロックの実測位置を測って補間 | 正確だが、SwiftUI の `ScrollView` に任意のオフセットを与える手段が macOS 14 に無い。`ScrollPosition` は macOS 15 以降 |
| 最低 OS を macOS 15 に上げる | 上の案のためだけに対応 OS を切るのは割に合わない |

**実装**

```
エディタ                                      プレビュー
NSTextView.characterIndexForInsertion(at:)     PreviewBlock.sourceLine
  → LineIndex で行番号へ                        （swift-markdown の SourceRange 由来）
  → topVisibleLine (Binding<Int>)  ──────────→  blockID(containing:) → ScrollViewReader
```

`characterIndexForInsertion(at:)` を使ったのは、TextKit 1 と TextKit 2 の
どちらで動いていても同じ答えが返るため。レイアウトマネージャに直接触ると、
どちらで動いているかを気にすることになる。

**割り切ったこと**

- ブロック単位でしか合わない（長い段落の途中では、その段落の先頭で止まる）
- エディタ → プレビューの一方向のみ。逆方向も入れるとスクロールの取り合いになる

仕様に「大幅にずれてしまう場合は、同期をキャンセルしてよい」とあるが、
ブロックに吸着させる方式なので、そもそも大きくずれることがない。

**ついでに直したこと**
`updateNSView` で `textView.string != text` と比較していた。
`NSTextView.string` は呼ぶたびに文字列を作り直すため、スクロールのたびに
本文全体をコピーすることになっていた。Coordinator 側に控えを持って比較するよう変更。

### B-11. 定規を付けると、AppKit がタイトルバーに縦線を引く

**症状**
行番号の区切り線が、閉じるボタンの脇を通ってタイトルバーの中まで伸びる。
ライトでもダークでも同じ。

**まず自分を疑ったが、違った**
`drawHashMarksAndLabels(in:)` は自分の `bounds` に閉じ込めてある（B-9）。
計測でも定規はタイトルバーの下に収まっていた。

```
ruler→window       = (0, 0, 30, 791)
contentLayoutRect  = (0, 0, 1061, 791)   ← タイトルバーを除いた領域と一致
window.frame.height = 843                ← 上の 52pt がタイトルバー
```

**切り分け**
アプリ自身に `NSThemeFrame` を `cacheDisplay` させて PNG に焼き、画素を数えた。
（この環境では画面収録の権限が無く、スクリーンショットが撮れないため）

| 試したこと | タイトルバーの縦線 |
|---|---|
| 区切り線をマゼンタにする | 色が変わらない → **自分の線ではない** |
| 定規の幅を 30pt 広げる | 線も一緒に移動（x=29pt → 59pt）→ **定規に追従している** |
| 行番号を消す（定規を外す） | **消える** |
| `window.titlebarSeparatorStyle = .none` | 消えない |
| ツールバーの項目一覧を確認 | 分離子（tracking separator）は入っていない |

`NSScrollView` に定規があると、AppKit が定規の右端をなぞる線を
タイトルバー（`_NSTitlebarDecorationView` の領域）まで引く。公開の設定では消せなかった。

**対処: `NSRulerView` をやめる**

| 案 | 結果 |
|---|---|
| スクロールビューに自前のビューを足し、`contentInsets` で本文を右へずらす | **失敗。** SwiftUI がまだ大きさを決めていない時点で `contentInsets` を入れると、テキストコンテナの幅が 7pt まで潰れて本文が消えた（D-14 と同じ罠） |
| **テキストビューの左右の余白（`textContainerInset`）を広げ、`drawBackground(in:)` で左側へ描く** | **採用** |

番号が本文と同じ座標系に乗るので、スクロールへの追従も行の位置合わせも
AppKit 任せで済む。`usedRect` に `textContainerOrigin` を足すだけになった。

**代償**: `textContainerInset.width` は左右に等しく効くので、右の余白も
同じだけ広がる（12pt → 42pt）。テキストコンテナの幅の決め方に触れずに済むので、
折り返しの追従を壊さないことを優先した。

**教訓**
「線が出ている」と「その線を自分が描いた」は別のこと。
**色を変えて、動かして、消してみる。** 三つとも一致して初めて犯人が確定する。
最初の計測（`convert(bounds, to: nil)`）は正しかったのに、
症状と噛み合わないので疑ってしまった。計測が正しいときは、前提の方が間違っている。

**細かい落とし穴**: `NSView.enclosingScrollView` は、スクロールビューの
**直接の子では `nil` を返す**（クリップビューの中に居ることを前提にしている）。
`superview` は `NSScrollView` なのに `nil`、という食い違いで一度止まった。

### B-10. 「システムのハイライト色」を文字色に使うと読めない

**やろうとしたこと**
カーソルのある行の番号を、OS のハイライトカラー設定の色で太字にする。

**素直に実装すると失敗する**
ハイライトカラーそのものは `NSColor.selectedTextBackgroundColor` だが、
これは**選択範囲の背景**用に明度を上げてある色で、文字色には向かない。
利用者の設定（黄色）で実測した値:

| 色 | ライト | ダーク |
|---|---|---|
| `selectedTextBackgroundColor`（ハイライト色そのもの） | `#FFEEBE` | `#8B7A3F` |
| `selectedContentBackgroundColor`（選択項目の背景色） | `#E1AC15` | `#D19E00` |
| `controlAccentColor` | `#FFC726` | `#FFC600` |

ライトの背景 `#F5F5F5` に対するコントラスト比は、
`selectedTextBackgroundColor` が **1.43**、`selectedContentBackgroundColor` が **1.90**。
前者は太字にしても背景に埋もれて読めなかった（画像で確認）。

**採用**
`selectedContentBackgroundColor` を文字色に使う。同じハイライト／アクセント設定から
導かれる色なので、利用者が黄色以外に変えれば追従する点は変わらない。

**「見分けが付くか」を明度で測ってはいけない**
ふつうの行番号は灰色 `#A8AAB2`。琥珀色 `#E1AC15` との**コントラスト比は 1.12** しかない。
明るさが近いだけで、実際は色相で明確に区別できる。
回帰テストは彩度で見るようにした（灰色は彩度ほぼ 0、強調色は 0.9 前後）。

**焦点の出入りを知る手段が AppKit に無い**
ファーストレスポンダが変わったことを伝える通知は存在しない。
`NSTextView` を継承して `becomeFirstResponder()` / `resignFirstResponder()` を
拾う `FocusReportingTextView` を作った。

`window?.firstResponder` を見に行かないのは、`becomeFirstResponder()` の時点では
ウインドウ側がまだ更新されておらず、古い答えが返るため。自分で状態を持つ。

テキストビューは `NSTextView.scrollableTextView()` が作ったものを差し替えているが、
**TextKit 一式（テキストストレージ、レイアウトマネージャ、テキストコンテナ）は引き継ぐ**。
自分で組み直すと折り返しやスクロールの設定を作り直すことになり、
過去に何度も踏んだ落とし穴（D-14 のプレビュー）に戻る。

**描き直しの合図**

| きっかけ | 拾い方 |
|---|---|
| カーソルが動いた | `textViewDidChangeSelection(_:)` |
| 焦点が出入りした | `FocusReportingTextView.onFocusChange` |
| スクロールした | `boundsDidChangeNotification`（既存） |
| 本文が変わった | `textDidChange(_:)`（既存） |

### B-9. 行番号を出すと本文が消える

**症状**
行番号は正しく出るのに、本文の領域が単色に塗りつぶされてテキストが見えなくなる。

**切り分け**
オフスクリーンに焼いた PNG の色数を数えて、どこまでが正常かを1段ずつ確かめた。

| 状態 | 本文域の色数 |
|---|---|
| 定規なし | 822 |
| 定規を付けるが、何も描かない | 822 |
| 定規を付け、背景だけ塗る | **1** |
| 定規を付け、全部描く | **1** |

「付けるだけ」なら無事で「背景を塗ると」消える。犯人は描画の1行目だと確定した。

**原因**
`drawHashMarksAndLabels(in rect:)` に渡る `rect` を、定規の描画範囲だと思い込んでいた。
実際の値を出すと **スクロールビュー全体の大きさ** だった。

```
bounds = (0, 0,  31, 560)   ← 定規の幅
rect   = (0, 0, 520, 560)   ← 渡ってきた矩形。本文の上まで含む
```

`rect.fill()` が本文の上まで塗りつぶしていた。

**対処**
塗る範囲を必ず自分の `bounds` に閉じ込める。

```swift
let area = bounds.intersection(rect)
guard !area.isEmpty else { return }
theme.background.setFill()
area.fill()
```

**教訓**
描画メソッドに渡る矩形は「描いてよい範囲」ではなく「描き直しが要る範囲」であり、
自分の領域より広いことがある。**塗りつぶす前に自分の `bounds` と交差させる。**

回帰テストは `NSBitmapImageRep` に描かせて、定規の外の画素が
番兵の色のまま残っているかを見る形にした（`LineNumberGutterTests`）。
`area.fill()` を `rect.fill()` に戻すと落ちることも確かめてある。

**ついでに直したこと**
`Coordinator.appliedAppearanceName`（B-8 で足したもの）が `#if canImport(AppKit)` の
外に出ていて、iOS 向けビルドが通らなくなっていた。iOS ビルドは
`xcodebuild -destination 'generic/platform=iOS'` を回さないと気づけない。

### B-8. 「システム」に戻すと、エディタだけ前のテーマのまま残る

**症状**
ライト → システムに切り替えると、ヘッダーは暗くなるのに編集画面は白いまま。
クリックなど何か操作すると暗くなる。ダーク → システムでは起きない
（結果が同じなので気づけないだけ）。

**原因**
`.system` のときに `appearance = nil`（＝親から継承）を設定していた。
**AppKit は「明示指定 → 継承」に戻したとき、実効外観を下位のビューへ伝えない。**

実際の値（OS はダーク、ライト → システムに切り替えた直後）:

```
hosting.appearance    = nil(継承)  実効=DarkAqua   ← 正しく更新された
scrollView.appearance = nil(継承)  実効=Aqua       ← 古いまま
textView.appearance   = nil(継承)  実効=Aqua       ← 古いまま
```

`appearance` は正しく `nil` になっているのに、**実効外観だけが取り残される**。

**効かなかった手当て**（実測）

| 試したこと | 結果 |
|---|---|
| `viewDidChangeEffectiveAppearance()` を呼ぶ | 変わらず |
| 親の実効外観を入れてから `nil` に戻す | 変わらず |
| `documentView` を付け直す | 変わらず |
| **`NSApp.effectiveAppearance` を明示** | **直った** |

**対処**
`MarkdownAppearance.platformAppearance` を **`NSAppearance?` から `NSAppearance` に変えた。**
`.system` のときは `NSApp.effectiveAppearance` へ自分で解決する。**`nil` は返さない。**

副作用として、OS 側でテーマが変わったときに追従させる必要が出た。
`@Environment(\.colorScheme)` を読むことで SwiftUI の更新を受け、
比較も「解決後の外観の名前」で行うようにした（`.system` のままでも OS が変われば貼り直す）。

**教訓**
**「継承させる」は、状態を戻す操作としては信用できない。**
明示的な値を入れ続ける方が、どのビューがどの状態かを追える。
D-14 で「同期漏れという失敗の形そのものを無くす」と書いたのと同じ話だった。

推測で直そうとせず、`appearance` と `effectiveAppearance` を両方出力して初めて掴めた。

### B-7. 開いた直後だけハイライトが付かない

**症状**
ファイルを開いた直後は本文が単色。どこかを編集すると色が付く。

**原因**
`makeNSView` の中で、ハイライトを適用した**あとに**テーマを適用していた。

```swift
// 誤り
textView.string = text
highlight(...)                 // 装飾を貼る
apply(theme, to: scrollView)   // textView.textColor が全体を塗り潰す ❌
```

`NSTextView.textColor` と `font` は **本文全体**を一括で塗り替える。
ハイライトのあとに設定すると装飾が消える。
編集すると `textDidChange` で再ハイライトが走るので、そこで色が戻っていた。

**対処**
`makeNSView` を「テーマ → 本文 → ハイライト」の順に直した。
`updateNSView` と iOS 側（`makeUIView`）は元から正しい順序だった。

**混入した経緯**
テーマ切り替えを入れたとき、`apply` の引数を `textView` から `scrollView` へ変える際に
呼び出し位置も動かしてしまった。引数の変更に気を取られ、順序への影響を見落とした。

**再発防止**
`EditorSetupOrderTests` を追加。正しい順序で見出しが `heading` 色になることに加え、
**誤った順序だと本文色になってしまう挙動そのものをテストに書いた**。
「なぜこの順序でなければならないか」をコードに残すため。

**教訓**
属性を貼る処理と、ビュー全体の見た目を設定する処理は、**順序に依存する**。
後者が前者を破壊する側なので、必ず先に済ませること。

### B-6. ウインドウの角丸は変えられない（調査して結論、変更なし）

**きっかけ**
ウインドウの四隅が Chrome より丸く見える、という指摘。

**調べたこと**

| | 結果 |
|---|---|
| Nullnote と Chrome のビルド SDK | 両方とも macOS 26.5。SDK の違いではない |
| `NSWindow` の角丸を指定する API | AppKit のヘッダに存在しない |
| 旧デザインへ戻す Info.plist キー | 見つからず（`UIDesignRequiresCompatibility` は iOS 向け） |
| Chrome の `NSPrincipalClass` | `BrowserCrApplication` = 自前でウインドウを描いている |

**結論**
macOS 26 では標準ウインドウの角丸はシステムが決める。アプリからは指定できない。
Chrome が違って見えるのは、システムの枠を使わず自前で描いているため。

テキストエディットと並べて確認したところ、Nullnote と同じだった。**変更不要。**

**変えるとしたら**
枠なしウインドウにして、信号機ボタン・リサイズ・影・タイトルバーを自前実装することになる。
標準の挙動（フルスクリーン、タブ、ウインドウ復元）の一部を失い、
OS 更新でデザインが変わったときに自前部分だけ取り残される。**やらない。**

### B-5. ダークテーマでチェックマークが暗く沈む

**症状**
チェック済みのチェックボックスが、ライトでは白いチェック、ダークでは暗いチェックになる。

**原因**
`checkmark.square.fill` は**チェック部分を塗らずに背景を透かす**描き方。
単色で描くと、透けた先の色がそのままチェックの色になる。

| | 透ける先 | 見え方 |
|---|---|---|
| ライト | `#F5F5F5` | 白いチェック |
| ダーク | `#293238` | 暗いチェック ← これ |

**対処**

```swift
Image(systemName: "checkmark.square.fill")
    .symbolRenderingMode(.palette)
    .foregroundStyle(.white, Color(platform: theme.accent))
```

自前で図形を重ねる案（`RoundedRectangle` + `checkmark`）も同じ見た目になったが、
SF Symbol のままにした。文字とのベースライン合わせや、文字サイズ変更への追従を
自前で持たずに済むため。

**教訓**
`.fill` 系のシンボルは「塗り」ではなく「抜き」で形を作っているものがある。
**16pt では違いが分からなかった。60pt で描いて初めて見えた。**
色の検証は拡大して行うこと。

### B-4. 「保存先ディレクトリが選べない」— アプリの不具合ではなかった

**報告された症状**
「名前」だけ編集でき、「タグ」は入力できず、「場所」はグレーアウトして鍵アイコンが出る。

**真因**
押していたのは **⇧⌘S**。macOS の書類アプリでは、これは「別名で保存」ではなく **「複製」**。

メニューの実際の割り当て（`AXMenuItemCmdModifiers` を読んで確認）:

| 項目 | 割り当て |
|---|---|
| 保存 | ⌘S |
| **複製** | **⇧⌘S** |
| 別名で保存… | ⌥⇧⌘S |

（`閉じる = ⌘W` / `すべてを閉じる = ⌥⌘W` と一致するので、この読み取りは正しい）

複製された書類はまだディスク上に無いので、名前は付けられても**場所とタグは無効**になる。
ウインドウ名が「roundtrip のコピー2」だったのが決定的な証拠だった。

**Windows / Adobe 系では ⇧⌘S が Save As なので、間違えやすい。**

**入れた対処**
原因とは別に、保存パネルを既定で展開表示にした（`AppSettings.registerDefaults()` で
`NSNavPanelExpandedStateForSaveMode` を登録）。折りたたみ状態だと保存先が
「場所」ポップアップだけになるので、最初からファイルブラウザが開くようにした。
`register` なので、ユーザーが自分で畳めばその選択が優先される。

**⇧⌘S を「別名で保存」に付け替えなかった理由**
SwiftUI で付け替えるには `CommandGroup(replacing: .saveItem)` で
保存グループ全体を差し替え、保存・別名で保存・複製を自前で実装し直すことになる。
プラットフォームの慣習に逆らううえ、得るものが釣り合わない。

**調べて分かった副産物**

- `net.daringfireball.markdown` は LaunchServices に正しく登録されている
- サンドボックスアプリの保存パネルは別プロセス（`openAndSavePanelService`）で動くため、
  アプリ側の AX ツリーには中身が出ない。System Events では中を調べられない

**教訓**
UI の見た目から原因を推測して回るより、**メニューの実際のキー割り当てを読む**方が速かった。
「どの操作をしたか」を最初に確定させること。

## 検証方法についての記録

この環境では画面収録とアクセシビリティの権限が無く、
`screencapture` と `osascript` のキー操作送信が使えなかった。

**代わりに使った手段**

| 確認したいこと | 手段 |
|---|---|
| ビューの見た目 | `NSTextView` / `NSHostingView` をオフスクリーンで PNG に焼く |
| アプリが起動したか | `pgrep` |
| ファイルを開けたか | System Events でウインドウタイトルを読む |
| メニュー構成 | System Events でメニュー項目名を読む |

**保存の検証について**
文字入力を伴う操作が自動化できず長らく未検証だったが、
利用者が実際に ⌥⇧⌘S で `~/Desktop/Sample.md` へ保存した形跡
（`NSOSPLastRootDirectory = "~/Desktop"` と実ファイル）で確認できた。
UI を動かせないときは、**アプリが残した痕跡を読む**方が早いことがある。

**注意**: System Events の `enabled` プロパティは、メニューを開く前は
標準項目まで `false` と報告する。有効・無効の判定には使えない。
